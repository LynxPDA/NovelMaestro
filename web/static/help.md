# Справка

## Быстрый старт: полный цикл за один проход

Ниже — путь от пустой папки до готового файла книги. Всё делается в браузере, ничего не нужно запускать в консоли после старта сервера.

1. **Запустите программу.** В папке NovelMaestro выполните `python3 run.py` (на Windows — `python run.py`), сервер поднимется на `http://localhost:8756` и браузер откроется сам. Флаг `--no-open` — без автозапуска браузера.
2. **Настройте модель.** Раздел «Настройки» → вкладка «Модель и сервер»: адрес сервера (`HOST`), ключ (`API_KEY`), модель (`MODEL`). Нажмите **«Проверить сервер»** — программа сделает один короткий запрос `/models` и скажет, отвечает ли сервер и есть ли в его списке ваша модель. Настройки сохраняются сами, кнопки «Сохранить» нет.
3. **Создайте проект.** Раздел «Проекты» → **«＋ Создать проект»**. Укажите раздел (ACTIVE), английское имя папки (например `my_book`), при желании — русское название, автора и жанры (они попадут в метаданные книги), выберите набор шаблонов (по умолчанию `General`). Сразу можно приложить обложку (jpg/png) и исходник книги (txt или epub) — они лягут в `source/`.
4. **Проверьте исходник.** Откройте проект → вкладка «Файлы» → папка `source/`: там должен лежать файл книги. Если его нет — загрузите перетаскиванием на список или кнопкой загрузки.
5. **Разбейте книгу на главы.** Вкладка «Запуски» → карточка **«Разбор исходника на главы»**: исходник из `source/` подставится сам, а режим зависит от файла — для epub «По TOC (epub)», для текста «Ручной (regexp)» с маркерами глав вроде `Глава \d+`. Нажмите **«Предпросмотр»** — увидите список будущих папок глав и текст любой из них; лишние секции (обложку, выходные данные) можно снять галочкой. Затем **«Запустить»**. Появятся папки `chapters/00000_1_Заголовок/…` с файлом `chapter.txt`.
6. **Соберите глоссарий.** Карточка **«Создание глоссария (LLM)»** → «Запустить». Модель прочитает текст и запишет в `ner.json` имена, термины, обращения, топонимы с переводами. На большой книге это долгий запуск: процесс идёт с прогрессом, глоссарий сохраняется по ходу.
7. **Проверьте глоссарий.** Карточка **«Проверка глоссария (LLM)»** → «Запустить»: модель предложит правки (переводы, типы, пояснения) в файл `tmp/ner_review.json`. Откройте вкладку **«Проверки»** → под-вкладку «Глоссарий (LLM)», пройдитесь по правкам («Принять» / «Отклонить» / «Откорректировать») и нажмите **«Применить»**. Применение — отдельная задача, модель для него не нужна.
8. **Переведите.** Карточка **«Перевод (LLM)»** → тип работы по умолчанию «Полный цикл: Перевод → Редактура → Полировка» → «Запустить». Под логом — таблица глав с клетками ✓/✗/⊘, она обновляется живьём. Результат: у каждой главы появляются `translated.txt`, `redacted.txt` и `polished.txt`.
9. **Проверьте перевод (по желанию, но полезно).** «Проверка перевода» найдёт остатки чужого текста, слишком короткие главы и нарушенную нумерацию (отчёт — в `logs/`, смотреть во вкладке «Проверки» → «Перевод»). «Проверка перевода (LLM)» ищет смысловые ошибки и предлагает правки — их принимают и применяют так же, как правки глоссария. «Оценка перевода (LLM)» даёт развёрнутый разбор качества с оценкой.
10. **Соберите книгу.** Карточка **«Компиляция TXT/EPUB/FB2»** → режим **EPUB** → «Запустить». Обложка, метаданные и страница поддержки подхватятся из `source/` сами, если файлы там лежат. Готовый файл — в корне папки проекта: `<имя_проекта>_<первая>_<последняя>.epub`.

Всё: файл можно открывать в читалке или публиковать. Дальше — по желанию: «Массовые замены» для последней правки имён, «Создание Wiki (LLM)» для справочника по книге, «История» для контрольных точек состояния.

> **Сколько это стоит времени.** Разбор и компиляция — секунды. Глоссарий и перевод — это запросы к модели: у книги на 300 глав полный цикл занимает часы, а не минуты. Запускать можно диапазоном глав (поле «Главы: [start] – [end]»), а не всю книгу сразу — так проще проверить качество на первых десяти главах и только потом гнать остальное.

## О программе

**NovelMaestro** переводит веб-новеллы с любого исходного языка (китайский, английский, корейский и другие) на русский с помощью больших языковых моделей (LLM). Программа берёт на себя рутину — разбор исходника, вытаскивание глоссария, сам перевод, проверки, сборку в готовые форматы, — но ключевые решения оставляет человеку: выбор промптов, проверку качества, финальную корректуру.

Интерфейс один — страница в браузере; ставить ничего, кроме Python и нескольких библиотек, не нужно. Сверху — панель навигации: **Дашборд** (сводка, активные запуски и история), **Проекты** (книги по разделам), **Шаблоны** (стартовые промпты для новых книг), **Заметки** (общая тетрадь, `projects/notes.md`), **Настройки** (конфиг), **Справка** (этот раздел). Справа в шапке — переключатель светлой и тёмной темы и меню «⋮»: версия, блок обновлений, «О программе» и «Выйти» (завершает вход; включается флагом `--auth`). На узких экранах пункты меню сжимаются до иконок.

Заметки бывают двух видов: общие (раздел «Заметки», один файл на все книги) и книжные (вкладка «Заметки» внутри проекта — `source/info.md`).

Два ускорителя на все экраны:

- **`Ctrl+K`** (работает и в русской раскладке — `Ctrl+Л`) — палитра команд: экран, вкладка проекта, любая книга. Enter — перейти, стрелки — выбрать, Esc — закрыть.
- **Индикатор запуска в шапке** — пока идёт работа, в шапке видна строка с прогрессом; клик открывает проект на вкладке «Запуски» с живым логом.

### Как устроен перевод

Книга проходит десять стадий — ровно в том порядке, в каком они стоят на вкладке «Запуски»:

1. **Разбор исходника на главы** — epub или txt превращается в папки глав;
2. **Создание глоссария (LLM)** — из текста извлекаются имена, термины и топонимы в `ner.json`;
3. **Проверка глоссария (LLM)** — модель предлагает правки глоссария, человек их принимает или отклоняет;
4. **Перевод (LLM)** — конвейер: перевод → редактура по глоссарию → стилистическая полировка;
5. **Проверка перевода** — алгоритмическая сверка оригинала и перевода: объёмы, остатки чужого текста, нумерация;
6. **Проверка перевода (LLM)** — модель ищет смысловые ошибки в готовых главах;
7. **Массовые замены** — быстрые регулярные замены по всем главам, без модели;
8. **Оценка перевода (LLM)** — развёрнутый разбор качества с оценкой по десятибалльной шкале;
9. **Компиляция TXT/EPUB/FB2** — сборка готовой книги;
10. **Создание Wiki (LLM)** — справочник по книге на основе глоссария и текста.

Стадии независимы: можно перевести десять глав, проверить их, поправить промпт и продолжить с одиннадцатой. Последовательность подсказывают сами карточки, но жёсткой очереди нет — важно лишь, чтобы к моменту перевода главы уже существовали, а к моменту компиляции — были переведены.

### LLM-сервер: какой выбрать и как подключить

Программа работает с любым сервером, который умеет формат OpenAI: HTTP-API вида `…/v1/chat/completions`. Это может быть локальная модель на вашем компьютере или облачный сервис.

- **Локальный сервер** — бесплатно, приватно, без лимитов на объём текста. Подойдёт [llama.cpp](https://github.com/ggml-org/llama.cpp) с любой открытой моделью в формате GGUF, а также vLLM, Ollama, LM Studio и подобные. Нужен достаточно мощный компьютер: 30-миллиардная модель требует порядка 20 ГБ видеопамяти (или оперативной, но тогда медленно).
- **Облачный сервер** — свой видеокарты не нужен, оплата по факту. [RouterAI](https://routerai.ru) даёт единый API (`https://routerai.ru/api/v1`) к сотне моделей с оплатой в рублях. Подойдут и другие OpenAI-совместимые сервисы.

Всё подключение — три поля на странице «Настройки» (вкладка «Модель и сервер», карточка «Подключение»):

```text
Сервер LLM   https://routerai.ru/api/v1   адрес API (у llama.cpp — http://localhost:8080/v1)
API-ключ     ваш ключ                     локальному серверу обычно не нужен
Модель       google/gemma-4-31b-it        имя модели на сервере
```

Кнопка **«Проверить сервер»** рядом с полями делает один короткий запрос `/models`: жив ли сервер, сколько моделей отдаёт и есть ли в списке ваша. Проверяется именно тот адрес, который введён в форме, — в том числе ещё не сохранённый. Те же настройки живут в файле `.env` в корне программы; шаблон — `templates/.env.example`. Файл содержит ключи и в git не попадает.

**Рекомендуемая модель для перевода** (на октябрь 2026 года) — `google/gemma-4-31b-it` с включёнными рассуждениями («Рассуждения» → «включены», уровень — `high`; блоки «Рассуждения модели» на той же вкладке). Модель хорошо держит русский язык и длинный контекст, а рассуждения заметно улучшают редактуру и полировку. Дешевле и быстрее — модели поменьше; качественнее — модели крупнее, если ваш сервер их тянет.

### Обновления

Меню «⋮» показывает текущую версию и результат последней проверки. Сервер сам проверяет GitHub Releases при запуске (одна короткая попытка в фоне; без сети — просто тихо), кнопка «Проверить обновления» делает то же по требованию, интерфейс переспрашивает раз в 6 часов. Доступный релиз помечает «⋮» точкой. В блоке видно номер и дату релиза, отрендеренное описание, отдельные ссылки на страницу релиза и список изменений, а если обновлений нет — строка «У вас последняя версия» и кнопка «Проверить снова».

Проверка по кнопке идёт в сеть, поэтому блок сразу перерисовывается: кнопка подписана «Проверяю…» и не жмётся второй раз, а результат появляется в том же открытом меню — нажимать ещё раз и обновлять страницу не нужно. Если сеть недоступна, это не выдаётся за «обновлений нет»: в блоке появляется строка «Проверить не удалось» с причиной, а прежний результат проверки остаётся.

Кнопка обновления работает по-разному — способ установки программа определяет сама по файлам-маркерам:

- **запуск из репозитория** — «Обновить до vX.Y.Z» перематывает ветку на релиз (быстрая перемотка, без слияний);
- **портативная сборка и копия исходников** — та же кнопка берёт файлы из zip-архива релиза и кладёт поверх текущих; ничего не удаляется;
- **установка в Docker** — кнопки нет: контейнер не может заменить собственный образ. Блок показывает команду хоста `docker compose pull && docker compose up -d`, интерфейс её не запускает.

Кнопка «Скачать архив» отдаёт тот же zip, что лежит в выпуске на GitHub, — для ручной распаковки поверх старой папки.

Данные обновление не трогает никогда: папки `projects/` и логи, `llm_profiles.json` и `.env`, очередь запусков, а в портативной сборке ещё и папку `python/` с интерпретатором (она занята процессом). Встроенные шаблоны — набор `General` и шаблон `.env.example` — принадлежат программе, а не книге: их поставляет релиз, и обновление кладёт их поверх. Наборы, созданные вами, не трогаются нигде и никогда. Если менялись зависимости, блок отдельной строкой покажет команду установки пакетов.

После обновления сервер перезапускается. В запуске из репозитория и в копии исходников он делает это сам: процесс сворачивается и поднимается заново с теми же флагами и портом, а страница висит на сообщении «сервер перезапускается» и обновляется сама, как только сервер снова отвечает. Портативную сборку и Docker перезапускают руками — об этом написано в том же блоке. Активные запуски стадий при перезапуске останавливаются.

## Управление проектами

### Разделы

Проекты лежат в папке `projects/` и разложены по разделам:

- **ACTIVE** — книги в работе;
- **HOLD** — отложенные;
- **DONE** — завершённые.

Разделы не высечены в камне: свои можно создавать, переименовывать и удалять (непустой раздел удалить нельзя — сначала перенесите или удалите книги). При переименовании в уже существующее имя разделы объединяются: книги переезжают в целевой, старый исчезает. Кнопка **«⚙ Управление разделами»** — в шапке раздела «Проекты».

### Создание проекта

В разделе «Проекты» нажмите **«＋ Создать проект»**. Мастер спросит:

1. **Раздел** — по умолчанию ACTIVE;
2. **Имя (английское)** — имя папки проекта: пишите латиницей, пробелы заменяются на `_`, остальные символы (кириллица, знаки препинания) вырезаются; если имя пришлось почистить, уведомление после создания скажет «(имя очищено)»;
3. **Название (русское), автор, жанры** — необязательно; попадут в метаданные книги (`source/metadata.yaml`);
4. **Шаблон** — набор стартовых промптов и файлов, по умолчанию `General` (универсальный, без привязки к языку). Файлы из его `prompts/` и `source/` копируются в проект.

Сразу же можно приложить **обложку** (jpg/png) и **исходник** книги — они окажутся в `source/`. Поле принимает txt/md/epub/zip, но для разбора нужен `.txt` или `.epub`: zip — это упакованный epub или текст, распакуйте его, а `.md` переименуйте в `.txt`.

Внутри проект получает каркас: `source/` (обложка, метаданные, исходник, заметки о книге), `chapters/` (главы и файлы их стадий), `prompts/` (промпты книги), `logs/` (логи прогонов) и `tmp/` (рабочие файлы: отчёты проверок, промежуточные копии глоссария, сборки).

### Управление проектом

На карточке проекта кнопка **«Управление»** открывает окно с действиями:

- **перенести** в другой раздел;
- **переименовать** — в поле «Новое имя» пишется новое имя папки: пустое и с символами `/ \ : * ? " < > |` не примется, занятое в этом разделе — тоже;
- **дублировать** — полная копия `имя_copy` рядом, для альтернативного перевода (если такое имя в разделе уже занято, копия не создастся — сначала переименуйте или удалите старую);
- **удалить** — только после ввода слова `УДАЛИТЬ`.

Там же показывается строка состояния: сколько папок глав и сколько из них переведено/отредактировано/полировано (`глав: 300 | 300/298/290`), плюс отметки о глоссарии, собранных файлах и wiki (та же строка видна на карточке проекта в списке).

### Конфиг — один на все книги

**Конфиг один** — страница «Настройки». Пять субвкладок повторяют группы настроек: **Модель и сервер**, **Перевод**, **Глоссарий**, **Проверки**, **Книга и файлы**, плюс локальная **Внешний вид** (она про ваше устройство, а не про книгу). Внутри — карточки блоков, в них поля с метками и подсказками. Метки, типы, варианты и значения берутся из одного реестра, поэтому название блока стадии — ровно то же, что имя этой стадии на вкладке «Запуски».

Что полезно знать про эту страницу:

- **Кнопки «Сохранить» нет.** Изменённое поле уходит в конфиг само, через полсекунды после последнего нажатия; подтверждение — уведомление внизу справа. Подпись в шапке молчит, пока сохранять нечего, показывает «сохраняю…» на время записи, а если ключ перекрыт переменной окружения — честно пишет «перекрыто окружением».
- **«Сбросить настройки»** на каждой субвкладке возвращает поля вкладки к встроенным значениям реестра (с подтверждением словом `СБРОСИТЬ`); соседние вкладки не трогаются. У «Внешнего вида» этой кнопки нет — там предпочтения браузера.
- **Секреты не выезжают в интерфейс**: `API_KEY` показывается маской — точка на каждый символ. Если поле не меняли, сохранённый ключ остаётся прежним. Под полем ключа — ссылка «Получить API-ключ».
- **Настройки самого сервера** (адрес, порт, токен доступа, папка проектов, лимит параллельных задач) в браузере не показываются: это настройка машины, а не книги. Они меняются флагами запуска (`--host`, `--port`, `--auth`, `--token`, `--projects-dir`, `--jobs-limit`, `--max-upload-mb`) или ключами `WEB_*` в `.env` и применяются после перезапуска; в Docker адрес задаёт команда запуска контейнера.

Файл на диске один: `WEB_ENV_FILE` (в Docker — `projects/.env` в постоянном томе, поэтому правки переживают обновление образа), иначе корневой `.env` программы. В docker-compose задают только обвязку (`WEB_*`, `TZ`) — подключение модели и значения стадий живут в общем `.env`.

Приоритет настроек: **флаг командной строки > переменные окружения > выбранный профиль LLM > общий `.env` > встроенное значение**. Без `.env` программа не падает: работает на встроенных значениях.

**Внешний вид** — локальная субвкладка: тема редакторов, кегль редакторов и предпросмотра, язык подсветки для промптов и логов. Это привычки устройства (браузер, `localStorage`), а не конфиг книги: сохраняются сразу, полей реестра у них нет. Тема всего интерфейса — переключатель «луна/солнце» в шапке, он доступен с любого экрана.

### Профили LLM

Профиль — это полный набор настроек модели: сервер, ключ, модель, таймауты, повторы, потоки, температура, весь блок рассуждений. Профили нужны, когда серверов несколько: например, дома стоит llama.cpp, а в поездке вы работаете через облако, или черновик гоните быстрой моделью, а полировку — умной.

- **General** — встроенный профиль: его значения и есть общий `.env`. Ничего не дублируется, без выбора профиля всё работает как обычно; переименовать и удалить его нельзя.
- Свои профили создаются на странице «Настройки» → «Модель и сервер» → карточка «Профили LLM»: один выпадающий список и кнопки «+ Создать профиль», «Переименовать», «Удалить». Новый профиль создаётся **копией выбранного** — заполнять нужно только отличия.
- **Пустое поле профиля наследует General.** Это значит: если вам нужен другой сервер, но те же таймауты, заполняете только адрес, ключ и модель.
- Значения профилей лежат в `llm_profiles.json` рядом с общим `.env` (в Docker — в том же постоянном томе). Секреты и здесь под маской.

Профиль выбирает **каждая LLM-стадия** — это первое поле её формы, сразу за строкой «Главы»; подпись под полем показывает, что именно выбрано («Дачный — наследует General (http://192.1.8.8:9989, дом-модель, рассуждения: on)»). То есть в одной книге можно гнать перевод облачной моделью, а глоссарий править домашней. Выбор помнится за книгой и стадией: перезагрузка страницы, другой браузер или другое устройство возвращают ту же модель. У стадий без модели поля профиля нет вовсе. Смена профиля — не «изменённая настройка»: кнопка «Сбросить настройки» её не трогает.

### Выбор провайдера (RouterAI и OpenRouter)

Карточка «Выбор провайдера» нужна только **роутерам** — сервисам, у которых одну модель обслуживают несколько провайдеров: RouterAI и OpenRouter. Локальный сервер эти поля не читает: там модель одна, выбирать нечего, и пустые поля означают «ключ не отправляется вовсе».

Список провайдеров пишется одной строкой; разделитель — запятая, точка с запятой или пробел, регистр не важен: `DeepInfra, Google` и `deepinfra google` — одно и то же. Идентификатор — публичный `tag` провайдера (у RouterAI он виден в списке endpoint'ов модели на <https://routerai.ru/models>).

- **Приоритет провайдеров** — запрос уходит первому из списка, у кого есть эта модель; остальных роутер не касается.
- **Только эти провайдеры** — белый список: остальные не участвуют. Если модель не обслуживает никто из перечисленных, приходит ошибка 404.
- **Исключить провайдеров** — чёрный список: эти не участвуют. Исключили всех — снова 404.
- **Запасные провайдеры (allow_fallbacks)** — не список, а разрешение на замену: включено — если никого из приоритета у модели нет, запрос уйдёт любому другому допустимому; выключено — в том же случае вернётся 404 вместо чужого провайдера. На белый и чёрный списки флаг не влияет.
- **Страна серверов провайдера** — две буквы кода страны (`ru`): запрос обрабатывают только провайдеры с серверами оттуда. Это единственный фильтр, который сохраняется в резервных попытках.

Синтаксис `model@provider=...` прямо в имени модели и эта карточка одновременно несовместимы — роутер отвечает 400. Выбирайте одно из двух.

## Работа с проектом

### Общие принципы

- **Вкладки.** Внутри проекта — Файлы, Запуски, Редактор, Глоссарий, Проверки, Главы, Поиск, Статус, Настройки, Промпты, Логи, Заметки, История. Ссылку можно дать на любую вкладку: `#/project/ACTIVE/имя_книги/ner`; внутри проекта переключение вкладок адрес не меняет, но открытая вкладка, глава и панели «Редактора» запоминаются за книгой — вернувшись, вы попадёте туда же.
- **Главы.** Каждая глава — папка в `chapters/` с именем вида `00000_1_Заголовок`: нули добивают номер до ширины шесть, дальше номер и заголовок. Внутри — файлы стадий: `chapter.txt` (оригинал) → `translated.txt` (черновой перевод) → `redacted.txt` (после редактуры) → `polished.txt` (финальная версия). Имена фиксированы — по ним работает вся цепочка.
- **Глоссарий** — `ner.json` в корне проекта: термины с переводами, типами, частотой, контекстом. Его читают перевод, редактура и полировка.
- **Промпты** — файлы в `prompts/` проекта, у каждой стадии свой. Один файл может обслуживать несколько проходов: у перевода это теги `<translate>`, `<translate_lr>`, `<redact>`, `<polish>`.
- **Логи** — `logs/` (прогоны стадий) и `logs/chapters/` (по главам).
- **Рабочие файлы** — `tmp/`: отчёты проверок, файлы предложений, промежуточные копии глоссария, служебные файлы сборки. В контрольные точки истории они не попадают, а готовые книги лежат в корне проекта (см. «Компиляция»).

### Вкладка «Файлы»

Браузер файлов проекта: ходите по каталогам, смотрите и правите файлы, загружаете (кнопкой и перетаскиванием на список), скачиваете, создаёте файлы и каталоги («＋ Файл», «＋ Каталог»). Двойной клик по имени — редактор.

Строка списка — чекбокс, имя, метаданные и кнопки одного объекта: у файла «править», «скачать», «копировать», «переименовать», у каталога — «копировать» и «переименовать». Все действия — иконки, подпись читается при наведении.

Пока что-то выделено, кнопки тулбара заменяет панель выделения: счётчик «выделено: N», «переименовать» и «копировать» (при одном объекте), «скачать», «перенести в…», «удалить» (каталоги — вместе с содержимым) и «снять выделение». Чекбокс «выделить всё» — над строками.

Копия создаётся в той же папке и называется «Копия - имя»; если имя занято, добавляется номер — «Копия - файл.txt (2)». Каталог копируется целиком. Перенос делается одним запросом на всю выделку; папка назначения выбирается из дерева, текущая и сами выделенные каталоги из выбора исключены. Занятое имя или попытка положить каталог внутрь себя не ломают операцию: такой объект попадает в список «пропущено» с причиной.

Время изменения показывается по-человечески («3 ч назад»), точное — в подсказке. Файлы больше 5 МБ в редакторе не открываются — только скачивание. Выйти за пределы проекта (`..`, абсолютные пути, символические ссылки) нельзя.

### Вкладка «Редактор»

Две панели рядом: слева оригинал (`chapter.txt`), справа — перевод, редактура или полировка (по умолчанию то, что есть: полировка → редактура → перевод). Файл каждой панели выбирается своим списком, а кнопка «Два файла / Один файл» оставляет одну панель, когда нужен только перевод. Канонические имена видны и тогда, когда файла ещё нет: сохранение создаст его.

- **Подсветка терминов глоссария** — прямо по тексту; можно выключить, настроить размер n-грамм и порог нечёткого поиска.
- **«＋ в глоссарий»** — выделите фрагмент в оригинале и добавьте термин (термин, тип, перевод), не уходя из редактора.
- **Поиск** — `Ctrl+F` или лупа в заголовке панели; в панели поиска есть поле замены. Переход к тексту из «Проверок» и «Поиска» открывает редактор с уже подставленным запросом.
- **Переключение вида** у каждой панели: «Редактор» / «Рендер» (режим по умолчанию — по расширению файла; для простого текста предпросмотр показывает тот же текст с сохранением переносов).

### Вкладка «Глоссарий»

Таблица `ner.json`: правка прямо в строке, сортировка кликом по заголовку (по умолчанию `count` по убыванию), поиск по выбранным полям.

Настройки вкладки собраны за кнопкой «⋮»: режим «только зафиксированные», набор столбцов, типы, поля поиска, «Добавить столбец», «Добавить термин», «Удалить столбец», «Удалить по фильтру». В тулбаре остаются поле поиска и **«⬇ Экспорт для анализа»** — выгрузка JSON, записей текстом или имён по полу, с фильтрами по частоте, типам, исключениям и диапазону.

**Замок** на термине — важная вещь: зафиксированная запись не уходит на проверку LLM и не правится её правками. Строки помечены чекбоксами; выделение включает панель групповых действий — зафиксировать, снять замок, удалить (заблокированные при групповом удалении пропускаются).

### Вкладка «Проверки»

Каждая проверка — своя под-вкладка, выбор запоминается за книгой:

1. **Глоссарий (LLM)** — правки из `tmp/ner_review.json`;
2. **Перевод** — отчёты алгоритмической проверки (`logs/check_*.txt`);
3. **Перевод (LLM)** — правки из `tmp/translate_check_llm_review.json`;
4. **Оценка перевода (LLM)** — отчёт `tmp/translation_quality_assessment.md`.

**Отчёты проверки перевода** — список отчётов (`имя · ошибок: N`) слева и разбор выбранного справа: глава → папка → ошибки (критичные выделены красным). В шапке — тип проверки, диапазон, сколько глав проверено и с ошибками. Клик по ошибке открывает файл главы в том же редакторе с поиском по тексту ошибки, клик по папке — «Файлы» на этой главе. Кнопка «Очистить» удаляет все отчёты `check_*.txt`.

**Правки от модели** (глоссарий и проверка перевода LLM) устроены одинаково. Список правок со сводкой (всего / принято / отклонено / применено), у каждой — «Принять», «Отклонить», «Откорректировать» (Было / Стало / Причина), переход к тексту («→ Глава» — файл главы с поиском фрагмента, «→ Глоссарий» — вкладка с поиском термина). Правки одного термина группируются под общим заголовком. Над списком — массовые кнопки: «Принять все», «Отклонить все», **«Применить»**, «Очистить».

Кнопок «Сохранить файл» нет: любое действие с правкой сохраняет файл само, а применяются сразу все правки со статусом «принять». Строка «файл есть · размер» под списком — ссылка: она открывает сам JSON в редакторе тут же, на вкладке «Проверки» («← Назад» ведёт обратно к списку).

Применение — фоновая задача с уведомлением. Перед ним создаётся контрольная точка истории, чтобы всё можно было откатить (событие отключается настройкой `HISTORY_ON_APPLY`).

**Оценка перевода (LLM)** — просто отрендеренный markdown-отчёт с оценкой, сильными и слабыми сторонами и рекомендациями.

### Вкладка «История»

Контрольные точки проекта: снимки файлов книги (`ner.json` и главы) в хранилище внутри проекта — обычный git, но ставить git на компьютер не нужно. `tmp/`, `logs/` и служебные файлы в точки не попадают.

- **«＋ Контрольная точка»** — ручная метка с подписью «что в этом состоянии»; дата и время добавляются сами.
- **Автоточки**: перед применением правок проверок (включено) и после успешного запуска стадии (выключено по умолчанию — частые запуски дают много точек). Оба события переключаются настройками `HISTORY_ON_APPLY` и `HISTORY_ON_RUN` (страница «Настройки», группа «История (контрольные точки)»); при обычных правках файлов точки не создаются.
- **Возврат** — единственная кнопка у точки: файлы приводятся к её состоянию. Текущее состояние не пропадает: перед возвратом оно фиксируется отдельной точкой «Возврат к…», а все промежуточные точки остаются в истории.
- **Сравнение** — выделите две точки чекбоксами, в панели выделения появится «Сравнить выбранные точки». Пара всегда сравнивается от старой к новой, поэтому статусы файлов не переворачиваются. Таблица покажет добавленные, изменённые и удалённые файлы; у больших файлов вместо «+/−» строк стоит «много» — точные числа видны в самих изменениях файла (клик по строке). Зелёное — добавленные строки, красное — удалённые, серое — контекст.
- **Списки страницами**: у большой книги точек десятки, а изменённых файлов тысячи, поэтому и точки, и файлы отдаются порциями — в шапке ОБЩЕЕ число, под списком кнопка «Показать ещё» со счётчиком остатка.

### Вкладка «Главы»

Названия глав: список глав с редактируемой первой строкой файла (тип — chapter / translated / redacted / polished; по умолчанию polished). Диапазон — двумя полями, пропущенные главы стоят серыми ячейками. Кнопка «Сохранить» пишет все правки разом — с приведением текста к единой форме юникода (NFC, чтобы одинаково выглядящие буквы не различались), — и даёт отчёт: сколько обновлено, сколько глав не нашлось, какие были предупреждения. Рядом — «Удалить файлы» выбранного типа за диапазон (с подтверждением словом `УДАЛИТЬ`; необратимо). Удобно, когда после разбора хочется привести заголовки к единому виду.

### Вкладка «Статус»

Наглядная готовность книги. Сверху четыре карточки сводки: сколько глав, сколько из них переведено/отредактировано/полировано (`пер/ред/пол`), сколько терминов в глоссарии и статей в wiki. Ниже три полосы — перевод, редактура, полировка — с процентом и строкой «Отсутствуют главы: 75, 89, 361-717»: номера сжимаются в диапазоны, поэтому сотни пропусков читаются одной строкой. Длинный список по умолчанию свёрнут, кнопка «весь список» раскрывает его (раскрытость запоминается), полный текст есть и в подсказке.

Диапазон глав — от первой до последней существующей папки, поэтому пропущенная папка исходника видна наравне с отсутствующим файлом стадии. Внизу — таблица по главам с клетками «пер/ред/пол» (✓ есть, · ещё нет).

### Вкладка «Настройки»

Только данные книги, ничего про модель:

- **обложка** — выбор файла-картинки из `source/` с предпросмотром, загрузка и удаление; удаление без выбранного файла убирает каноническое `source/cover.*`;
- **метаданные epub/fb2** — YAML из `source/` с редактором (по умолчанию `metadata.yaml`);
- **файл страницы поддержки** — txt из `source/` с редактором (по умолчанию `donate.txt`).

У обоих файлов есть кнопка «Из шаблона»: содержимое берётся из шаблона, а сохранение остаётся за вами. Какой именно файл обложки и метаданных попадёт в конкретную сборку, выбирается в форме стадии «Компиляция».

Собственного `.env` у книги нет. Поля запусков, изменённые для одной книги, — состояние самой книги (`tmp/ui_state/`), поэтому их видно с любого устройства, и они переезжают вместе с копией книги. Профиль LLM для стадии выбирается там же, где и все поля, — в форме стадии на вкладке «Запуски».

### Вкладка «Промпты»

Список `prompts/` проекта открывает файл в редакторе с предпросмотром markdown/html; кнопка «Сохранить» пишет правки. Слева от редактора живут действия с самим составом папки: «Создать» заводит новый файл, «Из шаблона» копирует промпты любого набора `templates/*`, «Очистить» удаляет все промпты книги (каталог `prompts/` остаётся, стадии без файла переходят на встроенные промпты). У «Из шаблона» два способа: один файл (любой из любого набора, имя в книге можно поменять) или весь набор сразу — тогда в книгу приезжают все промпты выбранного набора, и виден их список до копирования.

| Стадия | Файл по умолчанию | Теги |
| --- | --- | --- |
| Перевод | `pipeline_prompt.txt` | `<translate>`, `<translate_lr>` (расширенный) |
| Редактура | `pipeline_prompt.txt` | `<redact>` |
| Полировка | `pipeline_prompt.txt` | `<polish>` |
| Глоссарий | `ner_prompt.txt` | `<prompt_pass1>`, `<prompt_pass2>` |
| Проверка глоссария | `ner_check_prompt.txt` | `<prompt_ner_check>`, `<prompt_rag>` |
| Проверка перевода (LLM) | `translate_check_prompt.txt` | `<prompt_translate_check>` |
| Оценка перевода (LLM) | `translate_quality_prompt.txt` | `<prompt_assessment>`, `<prompt_assessment_summary>` |
| Wiki | `wiki_prompt.txt` | `<prompt_wiki_article>` + JSON-теги |

**Плейсхолдеры:** `{ner_block}` (перевод, редактура, полировка), `{original_text}` (входной текст; в переводе и полировке это обязательный плейсхолдер — если его нет, в лог уйдёт предупреждение, а текст допишется после промпта), `{translated_text}` (редактура, оценка), `{female_names}` / `{male_names}` (имена из глоссария по полу), `{chunk_text}`, `{ner_json}`, `{glossary}`, `{fields}`, `{rag_block}`, `{batch_text}`, а для расширенного перевода — `{dict_block}`, `{rules_block}`, `{fewshot_block}`.

**Разметка запроса.** Содержимое `<system>…</system>` уходит в системное сообщение модели, весь остальной текст (в том числе `<user>…</user>`) — в пользовательское. Без разметки весь промпт уходит в пользовательское сообщение. Теги пишутся с начала строки.

**Что важно знать про промпты:**

- В промптах используются только реально обрабатываемые программой теги-этапы и разметка system/user; данные размечаются текстовыми маркерами («=== ГЛОССАРИЙ ===», «=== ОРИГИНАЛ ===»). Фиктивной XML-разметки данных нет.
- Файл **с тегами** обслуживает сразу несколько проходов. Промпт стадии читается только из своего тега: файл без нужного тега — не «промпт этапа целиком», стадия остаётся на встроенном промпте и пишет предупреждение в лог.
- **Проверка промпт-файла** идёт сама: при открытии формы стадии, при смене выбранного файла и при сохранении в редакторе. Жёлтый треугольник рядом с кнопкой «Редактировать» означает замечания — нет тега режима, в тексте нет переменной, в служебном теге битый JSON; список виден в подсказке. Проверяются все режимы стадии, а не только выбранный. «Внешний промпт не выбран» замечанием не считается — стадия честно работает со встроенным.
- **Кнопка у поля промпта зависит от выбора.** Выбран файл — «Редактировать» (правка прямо из запуска); не выбран ни один — «Из шаблона»: в модалке выбираются набор `templates/*` и промпт в нём, «Скопировать» кладёт файл в `prompts/` книги под именем из набора и сразу выбирает его в поле. Своих файлов у поля нет: произвольный текст кладётся во вкладке «Файлы» → `prompts/` и появляется в списке сам. У поля файла не-промпта (метаданные сборки, страница поддержки) пустой выбор даёт «Загрузить» — там файл грузят в `source/`.
- **Глоссарий (NER)**: модель должна вернуть строгий JSON-массив без markdown-обёртки. Поля: `term` (оригинал), `reading` (произношение — пиньинь, ромадзи, романизация; для латиницы — само написание), `type`, `translation`, `notes`, `context`. Программа понимает и `pinyin`, и `reading`.
- Промпты — контент проекта. Набор `General` — универсальная основа без привязки к языку; языковые особенности (титулы, частицы, обращения, транскрипция имён) дописываются в своём наборе шаблонов или прямо в промптах книги.

### Вкладка «Логи»

Список `logs/` и `logs/chapters/`, просмотр выбранного файла, «Автообновление» (догружать хвост каждые 1,5 с с автопрокруткой) и удаление логов. История запусков видна на «Дашборде» («Последние запуски»), а подробности каждого прогона — здесь.

### Вкладка «Поиск»

Одна строка текста ищет по файлам книги целиком, без индексов: что лежит на диске, то и находится. Ниже строки — выбор охвата: группы файлов с подписями по кластерам (у групп глав названиями служат имена стадий — chapter, translated, redacted, polished, у остальных подписи человеческие: «Заметки книги», «Промпты», «Отчёты проверок», «Логи»). Кнопки «Только главы» и «Все группы» ставят группы целиком.

По умолчанию ищутся оригинал и полировка глав, глоссарий и заметки книги — логи и отчёты включаются вручную. «регистр» — учитывать регистр букв (по умолчанию нет); «Контекст:» — сколько символов брать до и после совпадения (по умолчанию 60, не больше 300). Минимум два символа в строке поиска.

Результаты всегда полные (ни по числу совпадений, ни по числу файлов ничего не обрезается), а длинный список файлов листается страницами по 25 штук. Строка результата — номер строки и фрагмент с подсветкой. Клик по имени файла открывает его в том же однофайловом редакторе, что и в «Проверках»: вкладка «Поиск» никуда не уходит, панель поиска редактора уже открыта с этим запросом, а «← Назад» возвращает к результатам с той же страницей. Клик по `ner.json` открывает вкладку «Глоссарий» с подставленным текстом — там поиск идёт по всем полям записи и показаны все столбцы.

### Вкладка «Заметки»

Заметки о книге — `source/info.md`, markdown-редактор с предпросмотром. Сюда удобно складывать особенности языка, принятые переводы имён, ссылки на первоисточник: файл копируется из шаблона вместе с проектом.

## Шаблоны

Каталог `templates/` — стартовые файлы для новых проектов:

- **общий шаблон конфига** `.env.example` в корне;
- **наборы по типу книги** — подпапки: `General/` (универсальный) с `prompts/` (стартовые промпты всех стадий) и `source/` (metadata.yaml, donate.txt — страница поддержки, info.md — заметки о книге).

При создании проекта выбранный набор копируется в книгу — только файлы верхнего уровня из `prompts/` и `source/`; существующие файлы не перезаписываются.

Вкладка «Шаблоны» позволяет:

- **открывать и редактировать** файлы набора, скачивать их, переименовывать и удалять (для `General` доступны только просмотр и скачивание — системный набор защищён от изменений);
- **создавать новые наборы** (с готовым каркасом `prompts/` + `source/`), копировать, удалять; каталоги внутри набора неизменяемы — можно только открыть их;
- **загружать файлы** в набор (в `General` нельзя).

Зачем свои наборы: язык у книг разный. Китайская новелла требует одних правил обращения с титулами и транскрипцией, корейская — других. Один раз настроенный набор потом выбирается в мастере создания проекта, и каждая новая книга начинается с правильных промптов.

## Запуски

### Общая информация

Стадии запускаются на вкладке «Запуски» проекта (кнопка «Запуски» в списке проектов ведёт туда же). Каждая стадия — карточка с формой параметров и кнопкой **«Запустить»**. Кнопки «Сохранить» у формы нет: значения сохраняются сами.

Форма у стадии одна, все её поля берутся из реестра настроек. Сервер, ключ, модель и режим рассуждений в полях стадии не правятся: их приносит профиль LLM — первое поле формы у каждой LLM-стадии (см. «Профили LLM»).

Поля предзаполняются действующими значениями конфига. Кнопка **«Сбросить настройки (N)»** в шапке панели возвращает изменённые поля к значениям конфига — подсказка показывает каждое поле как «сейчас → значение конфига». Изменённые для этой книги значения остаются в самой книге (`tmp/ui_state/`), поэтому переживают смену браузера, домена и устройства. Запись отложена на полсекунды после последнего нажатия — одна на пачку изменений, а подпись в шапке панели показывает «изменено N · сохраняю…» или «изменено N · сохранено».

**Диапазон глав** у стадий — единая строка «Главы: [start] – [end]». Это параметр запуска книги, а не настройка: пустое поле значит «с первой» и «до последней». У «Оценки перевода (LLM)» конечная глава контролируется по бюджету запроса: поле остаётся ручным, влезшая в бюджет глава сохраняется, не влезшая — обрезается до последней влезающей.

**Во время запуска** — живой лог и строка прогресса: счётчик «N/M · X%», фаза («Глава 2 · Перевод») и оценка времени завершения («осталось ≈ 12 мин · завершение 14:35»). Строка одна на все места: панель лога, карточка активного запуска, Дашборд, индикатор в шапке. Названия фаз русские, из реестра — «Перевод / Редактура / Полировка». Пока задача работает, строка видна даже до первого события («ожидание первого результата…»). Кнопка **«Стоп»** останавливает запуск вместе с дочерними процессами.

Два запроса сразу на один проект запрещены: стадии перезаписывали бы одни и те же файлы (ответ 409 «уже обрабатывается»). Общий лимит одновременных запусков — `WEB_JOBS_LIMIT` (по умолчанию 2).

История запусков — на «Дашборде»; при переносе проекта в другой раздел или переименовании журнал следует за книгой.

**«Предпросмотр запроса»** (у LLM-стадий) — кнопка, которая собирает первый запрос стадии (первую порцию текста) без обращения к сети и показывает его текст, размер и разбивку по частям. Лучший способ понять, что именно уйдёт модели, и не переплатить за это.

### Разбор исходника на главы (epub)

Стадия **«Разбор исходника на главы»** (`epub_to_chapters`), без модели. Исходник — `.epub` или `.txt` из `source/`; список фильтруется режимом: «По TOC» принимает только epub. Если в `source/` лежит epub, он подставляется в поле сам — ваш осознанный выбор при этом не перекрывается. Мастер создания проекта принимает и zip-архив, но в списке поля его нет: распакуйте архив и загрузите `.txt` или `.epub`.

Режимы разбивки:

- **По TOC (epub)** — по структуре книги (spine/TOC/h1-h2), дубль названия главы в тексте удаляется;
- **Ручной (regexp)** — строки-маркеры: каждая строка, начинающаяся с любого паттерна, становится заголовком новой главы, вся строка целиком — названием (пример: `Глава \d+`);
- **По чанкам** — текст режется на куски заданного размера (поле «Размер чанка», ТОКЕНЫ), названия по маске «Chapter {num}».

Чекбокс **«Предварительная очистка текста глав»** (по умолчанию выключен) убирает пустые строки внутри глав — каждый абзац своей строкой; пустая строка остаётся только после первой строки файла, то есть между заголовком и телом главы. Пробелы и табуляция в начале строк убираются всегда, и без этой галки.

Ещё в форме: «Переопределить названия глав маской» (все заголовки → «Chapter N»), длина названия каталога (`title_limit`), смещение нумерации (первая глава = 875, если книга — продолжение цикла), тип выходного файла (`chapter.txt` по умолчанию) и «Очистить папки глав перед записью» (рекомендуется: иначе старые главы останутся рядом с новыми и попадут в конвейер).

**Предпросмотр разбивки** — обязательная привычка при первом разборе: чекбоксы секций показывают все будущие главы с размерами, снятие галочки исключает главу (остальные перенумеровываются при запуске), а список «Текст главы» даёт заглянуть в любую из них.

Замены и регулярные очистки до разбивки из формы убраны: правки текста после перевода делает стадия «Массовые замены» (в командной строке флаги `--clean-re` и `--replace-re` остаются).

### Создание глоссария (ner)

Стадия **«Создание глоссария (LLM)»** (`ner`). Входной файл не нужен: главы `chapters/*/chapter.txt` склеиваются в память (диапазон можно ограничить строкой «Главы»).

- Если `ner.json` ещё нет — создаётся новый; если есть — стадия **дообучает** его, добавляя новые термины к существующим.
- **Двухпроходная схема** (по умолчанию включена) заметно улучшает качество: первый проход вытаскивает кандидатов, второй сверяет их с текстом чанка.
- Параметры: размер чанка, порог дедупликации (насколько похожими должны быть написания, чтобы считаться одним термином), размер n-грамм для латиницы, поля для «голосования» при схлопывании дублей, длина поля `context`.

Как это работает внутри: по ходу работы термины складываются в словарь, а дубли схлопываются голосованием — если из пяти чанков четыре сказали «перевод А», побеждает он. Поля, которые не голосуют (`notes`, `context`, `translated_context`), получают одно значение; какое именно — решает настройка «Не голосующие поля»: последнее (как исторически), первое присвоенное, самое длинное или самое короткое. Для «самого длинного» есть ограничение в СИМВОЛАХ: победившее значение длиннее — обрезается. `context` пишется из чанка (предложение с термином), а не моделью, поэтому всегда хранит первое значение. Пустое значение ничего не перезаписывает ни в каком режиме.

Промежуточная копия `ner.json` сохраняется по ходу работы: упавший прогон не теряет термины уже обработанных чанков. Стадию можно смело перезапускать — она продолжит с существующим глоссарием.

### Проверка глоссария (ner_check)

Стадия **«Проверка глоссария (LLM)»** (`ner_check`) отправляет глоссарий модели, получает правки и пишет их в `tmp/ner_review.json` — человек принимает или отклоняет их во вкладке «Проверки», затем применяет. На этапе применения модель не нужна.

Ответ, где правок нет (в том числе пустой массив `[]`), — не ошибка: настройка **«Повторных запросов при отсутствии правок»** (`NER_CHECK_RETRY_EMPTY`, по умолчанию 0 — выключено) задаёт, сколько раз спросить заново, прежде чем принять «здесь всё в порядке». Осторожно с этим счётчиком: повторы умножаются на число порций, а в режиме RAG — ещё и на каждый термин, так что книга в 600 глав при 5 повторах стоит до шести раз больше запросов.

Режимы работы:

1. **Выбранные типы (одновременно)** — по умолчанию: весь отфильтрованный по выбранным типам список разом, порциями по бюджету запроса. Модель возвращает исправленные записи (только изменённые поля), программа сама сравнивает их с `ner.json` и пишет правки в файл предложений. Дальше человек и «Применить».
2. **Выбранные типы (по отдельности)** — каждый тип проверяется отдельно, уже по обновлённому глоссарию; правки дописываются в тот же файл предложений.
3. **Точечно по списку (RAG)** — уточнение спорных терминов. Список терминов (по строке на термин), для каждого в промпт уходят выбранные поля записи (term, type и translation — всегда) и подходящие фрагменты книги: полнотекстовый поиск собирает их равномерно по всей книге, в бюджет `rag_budget` (ТОКЕНЫ на термин). Модель уточняет ТОЛЬКО запрошенный термин; отличия пишутся в тот же файл предложений. Запросы по терминам идут параллельно, а файл сохраняется после каждого термина — упавший прогон не теряет уже полученные правки.

Режимы независимы: RAG-поля (список терминов, тип источника, бюджет) действуют только в режиме RAG, в остальных игнорируются; сами значения в форме сохраняются, так что вернувшись в RAG вы найдёте список на месте.

Во всех режимах менять сам термин (`term`) модели запрещено — только поля из блока «Поля в запросе LLM». `term`, `type` и `translation` — неотключаемые галочки (без типа и перевода проверять нечего), по умолчанию добавляются `notes` и `context`, если они есть в данных.

**Замок пригодится**: зафиксированные термины с проверки снимаются (настройка «Не проверять зафиксированные»), их же не трогают и правки при применении.

Применение создаёт контрольную точку истории. Есть и `--auto-apply` — авторежим без человека (в интерфейсе не выведен, только в командной строке).

### Перевод (pipeline)

Стадия **«Перевод (LLM)»** (`pipeline`) — сердце программы, конвейер над главами:

- **Перевод** — `chapter.txt` → `translated.txt`, с глоссарием и контекстом;
- **Редактура** — замена терминов по глоссарию, `translated_trace.json` → `redacted.txt`;
- **Полировка** — стилистическая шлифовка, `redacted.txt` → `polished.txt`.

**Тип работы** (поле «Тип работы») — от него зависит, какие шаги идут:

| Значение | Что делает |
| --- | --- |
| Перевод | только перевод |
| Редактура (исходник — Перевод) | редактура готового перевода |
| Полировка (исходник — Редактура) | полировка готовой редактуры |
| Полировка (исходник — Перевод) | полировка поверх перевода |
| Сокращённый цикл: Перевод → Редактура | два шага |
| Сокращённый цикл: Перевод → Полировка | два шага |
| Сокращённый цикл: Редактура → Полировка | два шага |
| **Полный цикл: Перевод → Редактура → Полировка** | по умолчанию, все три шага |
| Перевод с расширенным контекстом | перевод со словарём, правилами языка и примерами из `source/` |

Параметры:

- **Общий промпт-файл** — один файл с тегами `<translate>`, `<translate_lr>`, `<redact>`, `<polish>`. Пусто = автоподхват первого подходящего файла из `prompts/` (`pipeline_prompt.txt`). Нет нужного тега — предупреждение в лог и встроенный промпт.
- **Размер чанка** — ТОКЕНЫ, оценка (по умолчанию 7000). Действует для перевода и полировки в любом типе работы; редактура идёт главой целиком.
- **Бюджет запроса** — ТОКЕНЫ, оценка: потолок пользовательского запроса (чанк плюс все блоки контекста), 0 = без ограничения. Превышение — ошибка чанка. Это предохранитель, а не расчёт: если сервер маленький, поставьте бюджет меньше его контекста.
- **Минимальная частота терминов** — термины с частотой ниже порога не попадают в блок глоссария (0 — без фильтра); отдельная настройка для имён (`{female_names}`/`{male_names}`) — насколько часто имя должно встретиться, чтобы попасть в справочник полов. Сам нечёткий поиск терминов (порог схожести и размер n-грамм) настраивается на странице «Настройки»: в форме стадии этих полей нет.
- **Потоки** — сколько параллельных запросов; берётся из профиля LLM (поле «Потоков (1–16)» на «Настройках»).
- Для расширенного перевода — файлы `dict_file` (словарь в формате `ner.json`), `rules_file` (справочник по языку, txt/md), `examples_file` (пары «оригинал → перевод», JSON), число примеров на чанк и порог их схожести.

**Ответ засчитывается только с признаком конца генерации.** Поток, закрытый без него, повреждённый фрагмент ответа, ошибка роутера внутри ответа, пустой ответ — всё это обрыв: чанк повторяется целиком, а не записывается обрезанным. Так вы не получите половину главы, принятую за готовый перевод.

Под логом запуска — таблица «Главы · перевод → редактура → полировка»: строки — только главы заданного диапазона, клетки ✓/✗/⊘ обновляются живьём (✓ готово, ✗ ошибка, ⊘ пропуск, «·» стадия ещё не дошла).

### Проверка перевода (translate_check)

Стадия **«Проверка перевода»** (`translate_check`), без модели: алгоритмическая сверка оригинала и перевода. Результат — отчёт `logs/check_<тип>_<start>-<end>.txt`, смотреть во вкладке «Проверки» → «Перевод».

Что проверяется:

- **Объёмы.** По всей книге собираются отношения объёмов каждой пары «оригинал/перевод» (объём — в токенах, той же встроенной оценкой, что режет чанки). Типичное отношение — медиана по книге, обычный разброс — медианное отклонение от неё. Глава помечается, если её отношение вышло за медиану ± max(минимальный допуск, `K` × отклонение / медиана). `K` — поле «Чувствительность проверки объёма» (по умолчанию 5); `K = 0` выключает объёмные сравнения. Статистика собирается по ВСЕЙ книге: переведены 300 глав, а проверяете 1–7 — типичное отношение и допуск считаются из 300, помечаются только главы диапазона. У промежуточной стадии может не быть части глав — у каждой пары своя база, её размер виден в шапке отчёта. При базе меньше 5 глав допуск расширяется (иначе разброс выборки обманчиво узок); из одной главы допуск взять неоткуда — пара пропускается.
- **Regexp-проверки** — по одной на строку, всё найденное считается ошибкой, проверяются ВСЕ строки, включая заголовок главы. Предзаполненный набор ловит остатки чужого текста: лишние заголовки «Глава N», китайские и японские иероглифы, хирагану и катакану, корейский хангыль, латиницу (в том числе одиночную букву внутри русского слова — «sделать»), другие азбуки, чужие кириллические буквы (украинские і/ї/є/ґ, белорусское ў, сербские ј/љ/њ и прочие) и «первая строка не заголовок». Русская азбука не проверяется сознательно — она и есть текст перевода.
- **Слова-исключения** — совпадения, целиком равные одному из этих слов, в отчёт не попадают. Например, «Linux», если латиница в тексте допустима.
- **Минимальный размер файла** — файл меньше N байт (по умолчанию 3072) помечается как «слишком мал».
- **Последовательность глав** — первое число первой непустой строки должно быть ровно на 1 больше предыдущей главы; строка без числа (например «Пролог») последовательность не обновляет. Проверку можно отключить.

Битое regexp-правило не роняет запуск: стадия пропускает его с предупреждением «regexp-проверка №N пропущена» и продолжает.

### Проверка перевода (LLM) (translate_check_llm)

Стадия **«Проверка перевода (LLM)»** (`translate_check_llm`) ищет смысловые ошибки в главах (тип файла: polished / redacted / translated) и пишет накопительный файл правок `tmp/translate_check_llm_review.json` (поля: глава, файл, было/стало, тип ошибки, причина, статус, применено). Человек правит статусы во вкладке «Проверки» → «Перевод (LLM)» и нажимает «Применить»; перед применением создаётся контрольная точка истории.

Параметры: бюджет запроса (ТОКЕНЫ: главы одного пакета плюс запас 200 токенов на промпт; глава крупнее — режется на чанки), лимит правок на главу, минимальная длина правки, максимум изменённых символов, повторы при отсутствии правок. Файл правок сохраняется после каждой порции глав — упавший прогон не теряет готовые правки.

Ответ, где ошибок не нашлось, — не ошибка: настройка `TRANSLATE_CHECK_LLM_RETRY_EMPTY` (по умолчанию 0 — выключено) задаёт, сколько раз спросить заново, прежде чем принять «ошибок нет». При 0 честный ответ не оплачивается повторными запросами.

### Массовые замены (batch_replace)

Стадия **«Массовые замены»** (`batch_replace`), без модели и без интерактива: применяет к главам список регулярных замен (поле «Regexp-замены», по одной паре на строку в формате `паттерн -> замена`; пустая правая часть — удаление). Есть тип файлов, диапазон глав и предпросмотр «Предпросмотр замен».

Полезно для финальной чистки имён и терминов: переименовали героя в глоссарии — прогоните замену по готовым главам.

`^` и `$` означают начало и конец СТРОКИ (многострочный режим). Живые примеры (каждую строку — отдельным правилом; пояснение — не часть правила):

```text
^  ->
 +$ ->
(?i)бессмертный -> Бессмертный
^Глава\s+(\d+|\[Номер\])\s*$ ->
```

- первое правило убирает отступ в два пробела в начале строк;
- второе убирает пробелы в конце строк;
- третье меняет слово без учёта регистра;
- четвёртое удаляет ЛЮБУЮ строку-заголовок «Глава N», включая первую.

Правая часть бывает и одним пробелом: правило ` + -> ` (паттерн «один или больше пробелов», в замене ровно один пробел) сжимает любую цепочку пробелов в один. Один пробел в замене значим, иначе он был бы неотличим от удаления. Такая замена глазом невидима, поэтому предпросмотр и отчёт рисуют пробелы точками.

Если первый заголовок нужно оставить, а остальные убрать, добавьте lookbehind: `(?<=[\x0a])^Глава\s+(\d+|\[Номер\])\s*$ ->` — он требует перевод строки перед строкой, а у самой первой строки файла его нет. Для строк-разделителей (`* * *`, ряды точек) работает то же: `^[.*…][ \t]*$ ->`.

### Оценка перевода (LLM) (translate_quality)

Стадия **«Оценка перевода (LLM)»** (`translate_quality`) — развёрнутая рецензия: в промпт подставляются оригинал (`{original_text}`, chapter.txt) и перевод (`{translated_text}`, выбранный тип файлов), модель пишет оценку по десятибалльной шкале, сильные и слабые стороны, рекомендации.

Два режима:

- **Диапазон одним запросом** (по умолчанию) — одна оценка по пакету глав. Конечная глава считается по бюджету запроса (только содержимое глав, промпт не вычитается) и обновляется при изменении начала, бюджета, типа или промпта; больше последней главы книги не бывает. Если главы не влезают, пакет обрезается до целого количества глав, отсечённые указываются в отчёте.
- **Чанками всей книги** — книга режется на чанки по N целых глав, каждый оценивается отдельным запросом, а отчёты сворачиваются моделью в итоговое заключение. Можно ограничить число чанков и способ отбора (равномерно по книге или первые по порядку) и задать перекрытие соседних чанков.

Промпт — теги `<prompt_assessment>` (оценка) и `<prompt_assessment_summary>` (свёртка отчётов) в выбранном файле `prompts/`; между тегами можно писать комментарии. Результат — markdown-отчёт `tmp/translation_quality_assessment.md` с технической шапкой (дата, диапазон, пакет, бюджет, модель, сервер); смотреть во вкладке «Проверки» → «Оценка перевода (LLM)».

### Компиляция TXT/EPUB/FB2 (compile)

Стадия **«Компиляция TXT/EPUB/FB2»** (`compile`), без модели: собирает главы в книгу (нативно, без внешних утилит). Режимы:

- **TXT (Rulate)** — заголовки вида `# [Название :|: N]`: тег загрузки на Rulate;
- **TXT** — обычный текст, заголовки как в переводе, без markdown-префиксов;
- **EPUB**, **FB2** — полноценные книги с обложкой и метаданными.

**«Глав в части»** работает в любом режиме: указано число — диапазон разбивается на части по столько глав (файл на каждую часть); пусто или 0 — одна сборка целиком. Тип файлов глав — polished / redacted / translated / chapter.

**Обложка** — единое поле (jpg/png/webp/gif/bmp из `source/`) сразу для EPUB и FB2; по умолчанию подхватывается `cover.jpg` (или `cover.png`/`cover.webp`) из `source/`, пусто = без обложки. **Метаданные** — YAML из `source/`, по умолчанию `metadata.yaml`; кнопка «Редактировать» открывает выбранный файл прямо из формы запуска. **Страница поддержки** — txt из `source/`, по умолчанию `donate.txt` (шаблон лежит в `templates/General/source/`). Все три поля перепроверяются при каждом открытии стадии, поэтому только что загруженный файл подхватится сам, а осознанный выбор «—» (без файла) автоподхватом не перекрывается.

Готовые файлы пишутся в **корень папки проекта** и называются по имени проекта и диапазону: `<Имя_проекта>_<начало>_<конец>.epub`, `.fb2` или `_txt.txt` / `_txt-plain.txt`. Рабочие файлы сборки (заголовки, временные тексты) — в `tmp/`.

Заголовок главы определяется так: первая строка в файле вида «Глава N» → иначе первая непустая строка («Пролог. Пример» станет названием) → иначе «Глава N». Заголовок, взятый из первой непустой строки, из тела главы убирается.

### Создание Wiki (LLM) (wiki)

Стадия **«Создание Wiki (LLM)»** (`wiki`) генерирует справочник по книге на основе глоссария и текста: статьи о персонажах, местах, артефактах, со ссылками на связанные термины.

Источник текста — «Собрать из глав» (по умолчанию; склейка `chapters/*` выбранного типа, с диапазоном) или готовый txt-файл. Формат: обычный Markdown, Rulate-Markdown или Rulate-HTML (заголовки через `span font-size`, списки `<ul>`, разделители `<hr />`). Оглавление и якоря-ссылки — только в обычном режиме и когда вики не сохраняется главой (у Rulate их нет всегда).

**«Сохранить как главу»** — вместо файла (по умолчанию `wiki.md` в корне проекта) справочник добавляется последней главой `chapters/00000_{N+1}_Wiki_Новеллы/` с одним файлом выбранного типа. Удобно, если хочется, чтобы справочник попал в книгу.

Параметры: максимум терминов, минимальная частота (у выбора типов живой счётчик — сколько терминов попадёт в запрос при текущих значениях), типы (как в проверке глоссария, по умолчанию все), число фрагментов контекста на термин, на каком расстоянии (в ТОКЕНАХ) искать описание рядом с именем термина, размер чанка полнотекстового поиска (ТОКЕНЫ), бюджет запроса статьи (ТОКЕНЫ: данные термина плюс связи плюс фрагменты; 0 = без ограничения, превышение — фрагменты обрезаются с хвоста), пары типов для связей и их количество.

**Тонкая настройка поиска контекста** живёт в `wiki_prompt.txt` служебными JSON-тегами: `<wiki_markers>` — слова-маркеры описания по типам, `<wiki_default_markers>` — общие маркеры («*» в конце = любой суффикс: `выглядел*` ловит «выглядела», «выглядели»), `<wiki_type_names_ru>` — русские названия типов в оглавлении, `<wiki_relations_labels>` — заголовки секций отношений, `<wiki_skip_relations>` — типы без секции отношений, `<wiki_type_order>` — порядок разделов. Удалили тег — программа возьмёт встроенное значение. Это позволяет адаптировать wiki под другой язык или другие типы без правки кода.

## Регулярные выражения

### Диалект

В NovelMaestro используется диалект **Python `re`** — тот же, что в языке Python (на regex101 выбирайте режим Python). Это не PCRE: поддерживаются основные конструкции — классы символов, квантификаторы, группы, якоря, ленивые квантификаторы `*?` `+?` `??`, lookahead и lookbehind (`(?=…)`, `(?!…)`, `(?<=…)`, `(?<!…)`), именованные группы. Регистр по умолчанию чувствителен (стандартный inline-флаг `(?i)` его отключает), юникод включён.

Поля регулярных выражений держат **чистые стандартные выражения**: никаких кастомных флагов и комментариев — режимы задаются inline-флагами (`(?i)`, `(?s)` и т.п.), а «#» в паттерне — обычный символ.

Где регулярные выражения применяются:

- **Разбор исходника** — паттерны разбивки;
- **Массовые замены** — поле «Regexp-замены»;
- **Проверка перевода** — поле «Regexp-проверки»;
- **Прямой запуск скриптов** — `--split-re`, `--replace`, `--regexp-check`.

Перенос строки внутри паттерна пишется только как `\x0a` (или `[\x0a]`). Причина: многострочные поля (паттерны разбивки, проверки, список замен) лежат в общем `.env` одной строкой, где граница строки записана литералом `\n` — паттерн с собственным `\n` был бы разрезан пополам и превратился в два битых правила.

### Основы

| Конструкция | Значение | Пример |
| --- | --- | --- |
| `abc` | точный текст | `Глава` |
| `.` | любой символ, кроме переноса строки | `Глава.` — «Глава1» |
| `\d` `\w` `\s` | цифра / буква / пробельный | `\d+` — число |
| `[а-я]` `[0-9]` | класс символов | `[А-ЯЁ]` — заглавная |
| `[^…]` | отрицание класса | `[^ ]+` — всё до пробела |
| `*` `+` `?` | ноль и больше / один и больше / ноль или один | `\d*` — цифр может не быть |
| `{n,m}` | от n до m повторов | `\d{2,4}` |
| `^` `$` | начало / конец строки | `^本章完` — строка-маркер |
| `(…)` `\|` | группа / альтернатива | `Хунг(а\|у\|ом\|е)` |
| `\b` | граница слова | `\bГлава\b` |
| `\\.` `\\(` | экранирование спецсимвола | `\.` — точка |

В полях форм символы вводятся как есть, одной обратной косой чертой. При запуске из командной строки bash может понадобиться двойное экранирование: `"Глава \\d+"`.

### Обратные ссылки

Обратные ссылки позволяют вставить часть совпадения (группу) в замену. Группы нумеруются с 1 по порядку открывающих скобок: `\1`, `\2`, … `\9`; `\g<0>` — всё совпадение целиком; `\g<имя>` — именованная группа.

Примеры в формате NovelMaestro `паттерн -> замена`:

- `第(\d+)章 -> Глава \1` — «第12章» → «Глава 12»;
- `Хунг(а|у|ом|е) -> Хун\1` — склонения: «Хунга» → «Хуна», «Хунгу» → «Хуну»;
- `Глава (\d+) -> Глава №\1` — «Глава 5» → «Глава №5» (нужна группа: `\g<0>` вставил бы всё совпадение, включая слово «Глава»).

> Обратные ссылки `\1…\9`, `\g<0>` и `\g<имя>` работают во всех полях замен.

### Примеры с разбором

#### 1. Нормализация маркеров глав (разбор исходника)

```text
第(\d+)章 -> Глава \1
```

«第3章 测试» → «Глава 3 测试». Паттерн: литерал «第», группа `(\d+)` захватывает номер, литерал «章». Замена — «Глава » плюс `\1`.

#### 2. Удаление мусора из текста (массовые замены)

```text
^本章完 ->
```

Каждая строка, которая начинается с «本章完» (якорь `^`), удаляется целиком: пустая правая часть значит «удалить».

#### 3. Склонение имени (массовые замены)

```text
Хунг(а|у|ом|е) -> Хун\1
```

Группа-альтернатива ловит окончание, `\1` возвращает его в замену: «Хунга» → «Хуна», «Хунгом» → «Хуном».

#### 4. Удаление HTML-тегов (массовые замены)

```text
<[^>]+> ->
```

`<`, затем класс-отрицание `[^>]+` (любые символы до `>`), затем `>`. Правая часть пустая — совпадения удаляются. Ленивый вариант — `<.*?>`.

#### 5. Точный термин с границами (массовые замены)

```text
\bСюань\s+Цин\b -> Сюаньцин
```

`\b` — границы слова, `\s+` — один или больше пробельных символов: «Сюань Цин» → «Сюаньцин», а написанное слитно «Сюаньцин» не задевается.

#### 6. Разбивка по маркеру (разбор исходника)

```text
Глава \d+
```

Каждая строка, начинающаяся с «Глава <число>», становится заголовком новой главы; вся строка целиком — названием папки главы.

### Проверка регулярных выражений

Готовые выражения удобно отлаживать на [regex101](https://regex101.com/) в режиме Python. Помните: в интерфейсе NovelMaestro разделитель пары — `->` (первое вхождение), пустая правая часть означает удаление, а «#» в паттерне — литеральная решётка, не комментарий.
