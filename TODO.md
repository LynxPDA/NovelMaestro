## Исследование (диагностика по пунктам запроса)

### 1. Нет уведомления о результате применения проверок LLM

Вкладка «Проверка» (`web/static/project-views.js::reviewView`, ~стр. 2065):
`runApply` зовёт `POST /api/{ner|translate_check_llm}/review/apply` → `_review_apply`
(`web/api.py:1028`) → `_jobs_start` — задача уходит в фоновый JobManager,
а SPA показывает только `toast("Применение: запущено")` и **не отслеживает
завершение**. Ответ `{ok, job}` с `job.id` игнорируется.

- Статусы задачи: `running | done | failed | stopped` (`web/jobs.py`); получить
  статус: `GET /api/jobs/{id}`.
- Аналогичная проблема: «Пробный прогон» в той же карточке (тот же `runApply`).
- Прочие запуски — БЕЗ проблемы:
  - «Запуски» (`run-views.js::launch` + `attachStream`) — SSE-стрим доводит
    финальный статус до бейджа/лога ✓
  - дашборд (`app.js`) — только список задач, запуск оттуда не ведётся ✓
  - других мест с паттерном «запущено-без-итога» не найдено.

**Решение**: после старта задачи поллить `GET /api/jobs/{id}` (интервал ~2 с),
при терминальном статусе — toast «✅ … завершено» / «❌ … ошибка (см. лог)» /
«⏹ … остановлено» + перечитать review-файл в карточке. Реестр watcher'ов
ключом `проект:карточка` — повторный запуск гасит старый поллинг.

### 2. Опция отключения .bak (включено по умолчанию)

`.bak` создают только две стадии при применении правок:

- `scripts/ner_check.py`: `auto_apply()` (стр. 465) и `do_apply()` (стр. 551) —
  `shutil.copy2(args.input, args.input + ".bak")`;
- `scripts/translate_check_llm.py`: `apply_fix_entries()` (стр. 747) —
  `shutil.copy2(fp, fp + ".bak")`; вызывается из `do_apply` (стр. 904, 910)
  и авто-применения в `do_check` (стр. 1070).

Сборка argv — `web/stages.py::build_ner_check` / `build_translate_check_llm`
(циклы флагов `apply/auto_apply/dry_run`); поля форм — `STAGE_SPECS` обоих
стадий (после `dry_run`). Применение из вкладки «Проверка» — `_review_apply`
(`web/api.py`): параметры `{apply, dry_run}` — добавить `no_bak`.

**Решение**: флаг `--no-bak` (по умолчанию бэкапы создаются) в обоих скриптах;
проброс в `build_*` + поле `no_bak` (`bool`, default False) в обеих стадиях;
`_review_apply` принимает `no_bak` из body; в карточке «Проверка» — чекбокс
«не создавать .bak», отправляется при применении.

### 3. Список LLM-правок (как у алгоритмических) + переключение с редактором

Сейчас карточки «1 · Проверка глоссария (LLM)» и «3 · Проверка перевода (LLM)»
показывают review-файл **только** как JSON-редактор (CodeMirror). Алгоритмическая
проверка («2 · Проверка перевода», `renderCheckReports`) показывает отдельные
ошибки с переходом в файл главы — это эталон «информативно и красиво».

Форматы review-файлов:

- `ner_review.json`: объект `{создан, обновлён, вход, параметры?, правки:[…]}`,
  запись: `{этап, term, field, old, new, причина, статус: принять|отклонить,
  применено, дата применения?}` (правки глоссария ner.json);
- `translate_check_llm_review.json`: тот же каркас, запись: `{этап, глава, файл,
  тип, old, new, причина, статус, применено, дата применения?}` (правки текста
  глав; `файл` — абсолютный путь `chapters/<папка>/<тип>.txt`).
- API: `GET/PUT /api/{ner|translate_check_llm}/review` — уже есть; новых роутов
  не нужно (правка записи = чтение → обновление → PUT целиком).

**Решение**: в каждой LLM-карточке — переключатель «Список правок» / «Редактор
JSON» (по умолчанию — «Список правок», редактор остаётся как второй режим).
Список: сводка (всего/принято/отклонено/применено), таблица записей; у каждой —
кнопки «Принять», «Отклонить», «Откорректировать» (модалка: old/new/причина),
переход к тексту правки («→ Глава» — открыть файл главы в редакторе с поиском
фрагмента; для глоссария «→ Глоссарий» — таб ner с поиском термина). Логика
разбора/обновления — чистые функции в `ui-core.js` (node-тесты).

   режим сохраняется при переключении табов; JSON-редактор — как раньше.
