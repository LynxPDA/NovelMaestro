# core/settings.py — реестр настроек (одно место истины)

Одна таблица, где живёт каждая настройка: ключ в `.env`, метка, тип, значение по умолчанию, подсказка и владелец-стадия. До реестра одно значение содержалось в четырёх местах — константы `core/stage.py`, константы и argparse `cli/*`, литеральные `default` в `web/stages.py`, и третий экземпляр комментариями в `templates/.env.example`; при этом глобальные ключи вида `CHUNK_SIZE`/`TIMEOUT` не читал никто (единственная форма записи была `<STAGE>_<FIELD>`). Теперь дефолт пишется один раз здесь.

Структура: субвкладка (`Group`, их пять: llm — Модель и сервер, transfer — Перевод, glossary — Глоссарий, checks — Проверки, book — Книга и файлы) → блок (`Block`, карточка) → настройка (`Setting`). Отдельной субвкладки про веб-сервер нет: его блоки (`server_net`, `server_run`) идут последними в первой — у блоков реестра есть флаг `llm`, по нему SPA подставляет значения профиля (настройки сервера профиль не перекрывает). Внешний вид (темы и кегли) в реестр не попадает как конфиг: предпочтения живут в localStorage, а их карточки SPA рисует своей локальной субвкладкой «Внешний вид». Ключ = имя в `.env`: у стадийных настроек `<STAGE>_<FIELD>`, у общих (LLM, рассуждения, `WEB_*`) — без префикса. Чипсы выбора (типы/поля) — `noenv`: тип `hidden`, в `.env` не пишутся, их состояние живёт в localStorage. Служебные таблицы: `LLM_BLOCKS` (какие блоки относятся к профилю LLM — по ним SPA подставляет значения профиля), `SERVER_BLOCKS` (блоки веб-сервера), `LLM_ALIAS` (исторические имена полей стадии: `jobs`→`threads`, `retries`→`max_retries`), `STAGE_LLM_FIELDS` (какие LLM-поля уходят в argv стадии), `BLOCK_TITLES`, `NL`/`NL_LIT`.

`GROUPS` / `SETTINGS` / `BY_KEY` / `BY_BLOCK` / `STAGES` — сам реестр; `STAGE_TITLES` — название стадии ОДНО отсюда: его читают и карточки «Настроек», и спеки запусков (web/stages.py), иначе одна стадия звалась бы в двух местах по-разному; `groups()` — как рисовать; `settings_of(stage)` / `stage_fields(stage)` / `form_fields(stage)` (hidden-настройки в форму стадии не идут) / `defaults(stage)` — metadata и дефолты для спеки стадии (в `web/stages.py` их копировать нельзя); `env_key(stage,name)` — ключ поля; `llm_settings()` — LLM-поля одним блоком; `llm_form(stage,profile)` и `with_llm(stage,form,profile)` — подставляют значения профиля в form под историческими именами полей, поэтому сборка argv стадии не изменилась; `display_value(setting)` (секрет — «••••»), `block_payload(block_id)` и `groups_payload()` — отдача реестра SPA.

Чтение (слоёв четыре: реестр → общий `.env` → профиль LLM → `os.environ`): `env_file()` (путь общего `.env`; с 2026-10 он возвращается всегда — «файла ещё нет» не значит «конфиг не настроен») / `file_values()` (что выставлено в файле) / `layered_values(profile="")` (поверх файла — значения выбранного профиля, затем непустые переменные окружения: окружение остаётся рубежом деплоя) / `effective(key)` (bool парсится, у textarea литерал «\n» разворачивается) / `stage_values(stage)` — эффективные значения стадии / `llm_values(profile="")` — LLM-конфиг конвейера одним словарём: стадийных `PIPELINE_HOST`/`NER_MODEL`/`<СТАДИЯ>_API_KEY` нет, потоки тоже одна величина; `web_settings()`/`web_values()` — конфиг запуска сервера; `apply_cli_defaults(parser, stage)` вызывается в каждой точке входа `cli/`.

Запись: `sanitize(setting,value)` (значения — одной строкой: у textarea переносы сворачиваются в литерал «\n», у прочих — в пробел; `#` вне кавычек прячется в кавычки) / `write_values(ключ→значение)` перезаписывает общий `.env` по порядку реестра (пустое снимает ключ, без ключей файл удаляется) / `groups_payload()` — тот же реестр с текущими значениями для SPA; секретные поля отдаются как «••••».

## Профили LLM (несколько наборов настроек модели)

Профиль — полный набор LLM-настроек (сервер, ключ, модель, таймауты, повторы, предел ответа, потоки, температура, отношение длин и весь блок рассуждений): 16 настроек блоков `llm_conn`/`llm_net`/`llm_run`/`llm_reasoning`. Нужен, когда серверов несколько: «домашний» и «облачной» раньше означали переписывание общего `.env` руками.

**General** — встроенный профиль по умолчанию: его значения и есть общий `.env`, поэтому данных в двух местах нет и без выбранного профиля система ведёт себя ровно как до профилей; он не переименовывается и не удаляется. Остальные профили — **один `llm_profiles.json` рядом с общим `.env`** (в Docker — в том же постоянном томе): `{"profiles":[{"id","name","values","created","updated"}]}`, в `values` — только переопределения (ключи `.env` верхним регистром), пустое поле профиля наследует General; последний удалённый профиль убирает файл совсем.

API: константы `PROFILE_DEFAULT` (`general`) / `PROFILE_DEFAULT_TITLE` / `PROFILE_ENV` (`NM_LLM_PROFILE` — переменная подпроцесса) / `PROFILES_NAME`; файлы — `profiles_file()` (сосед общего `.env`; файла конфига нет — корень репо) / `profiles_read()` / `profiles_write(list)` / `profiles()` (General первым); чтение — `profile_get(id)` (пустой id и `general` — встроенный), `profile_values(id)`, `profile_display(id)` (General — эффективные значения конфига, остальные — свои переопределения; секрет под маской), `profile_slug(name,taken)` (латиница имени — slug, иначе `p1`, `p2`, …; id пишется один раз); CRUD — `profile_create(name,values)` (без значений — копия General: `profile_defaults()` — эффективные LLM-значения конфига, пустые ключи в профиль не пишутся), `profile_rename(id,name)` (id остаётся: на него ссылается выбор проекта), `profile_delete(id)`, `profile_save_values(id,values)`, `profiles_payload()`.

Куда выбор девается в web: поле **«Профиль LLM»** — ПЕРВОЕ поле формы каждой LLM-стадии (у стадии без модели поля нет), значение — состояние браузера по проекту+стадии (`localStorage nmProfile:<раздел>/<книга>:<стадия>`). У стадий одного проекта выбор свой: перевод на облачной модели, глоссарий — на домашней. `form_fields(stage)` ставит поле первым, `with_llm(stage,form)` читает его из формы и разбирает по историческим именам полей стадии, а подпроцесс получает `NM_LLM_PROFILE=<id>` — скрипты стадий читают реестр как читали, своего чтения `llm_profiles.json` у них нет. В CLI профиль — та же переменная окружения (или флаги `--host/--model` напрямую).

Дефолты подключения в реестре: `HOST=https://routerai.ru/api/v1`, `MODEL=google/gemma-4-31b-it`, `API_KEY` пусто.

# core/transport.py — единственная точка выхода в сеть (единственный HTTP-клиент)

HTTP-клиент в проекте один — `httpx`, и живёт он **только** здесь: `cli/`, `web/` и `run.py` не импортируют HTTP-библиотеки вовсе (страж `tests/test_architecture.py`; он же не даёт вернуть «запасной» клиент). Запасной не нужен: второй клиент — это второй адаптер, второй путь ошибок и второй набор тестов ради поведения, которое вызывающий не видит. Что даёт общий клиент: переиспользование соединений (конвейер бьёт в один сервер сотнями запросов) и раздельные connect/write/read таймауты.

`open_stream(url, *, headers, payload, connect_timeout, read_timeout)` — единственный способ POST-а в LLM; возвращает контекстный менеджер `ResponseStream`: `status_code`, `headers`, `iter_lines()` (байтовые строки тела по `\n`, `\r` отрезан, пустые строки отдаются как есть — пустая строка SSE = конец события; `[DONE]` и finish_reason видны читателю). Выход из контекста закрывает соединение, в том числе при `break` в середине стрима; запрос уходит на входе в `with`, поэтому «сервер лежит» прилетает именно там и тоже нормализуется.

Ошибки: `TransportError` (базовый) / `ConnectTimeout` (таймаут connect, отказ соединения, недоступен хост) / `ReadTimeout` (сервер молчит в теле; сюда же — нет соединения в пуле) / `BrokenStream` (обрыв тела, битый gzip/декодер). Гигиена стрима и политика ретраев живут в `core/common.py`. Прочее API: `client()` (общий `httpx.Client`), `reset_client()` (сброс — тестам), `BACKEND` (`"httpx"`), `python3 -m core.transport` — сводка.

# core/deps.py — реестр внешних зависимостей (активный стек в лог)

Роль — не имя пакета: роль закрыта, если работает хотя бы один её кандидат; кандидат без модуля — встроенный stdlib-фолбэк, он «установлен» всегда. Роли: HTTP-транспорт LLM (один кандидат `httpx`, обязателен — фолбэка сознательно нет), разбор `.env` (один кандидат `python-dotenv`, обязателен), поиск терминов по главам (pyahocorasick, иначе regex-фолбэк), прогресс-бары CLI (tqdm, иначе счётчик только строками лога), тесты (pytest + pytest-xdist). Только чтение: модуль ничего не устанавливает и поведение не меняет — его выбирают люди и лог.

`ROLES` (роли и кандидаты в порядке предпочтения) / `status()` → строки отчёта `{role, where, required, active, installed, degraded, pip_missing}` (`degraded` — роль на фолбэке: не ошибка, просто медленнее) / `format_status()` — одна строка для баннера/лога (web-сервер пишет её при старте) / `missing_hint()` — что доустановить одним pip-ом / `main()` — таблица для `python3 -m core.deps`.

# core/search.py — поиск по текстам книги (обычный проход, без индексов)

Книга — сотни файлов по несколько килобайт: обычный проход читает их за доли секунды, а FTS5-индекс означал бы второй слой (построение, инвалидация, разъезд с правками) при нулевом выигрыше. Индексов и кешей нет намеренно — результат всегда равен содержимому файлов.

Реестр групп (`SearchGroup`-кортежи `SEARCH_GROUPS`) решает, *что* именно читает поиск: `chapter`/`translated`/`redacted`/`polished` — артефакты стадий во всех папках глав, `ner` — `ner.json`, `notes` — `notes.md` и `source/info.md`, `prompts`/`reports`/`logs` — обход каталогов `prompts/`, `tmp/`, `logs/` (только текстовые расширения `TEXT_EXT`). `GROUP_IDS` — ключи, `GROUP_LABELS` — подписи для интерфейса, `DEFAULT_SCOPES` — что ищется по умолчанию (`chapter,polished,ner,notes`: тексты книги и глоссарий, без служебных каталогов).

API: `iter_project_files(project_dir, scopes=None, *, max_file_bytes)` — обход (главы — по номеру, каталоги — вниз по именам; пустые и oversized файлы пропускаются); `find_in_text(text, query, *, context, case_sensitive)` — все совпадения `[{line, start, end, text}]`, где `line` — номер строки с 1, `text` — строка, обрезанная до ±`context` **СИМВОЛОВ** (обрезок помечен «…»), `start`/`end` — границы совпадения внутри этого фрагмента (`text[start:end]` — само совпадение); `search_project(project_dir, query, scopes=None, *, context, case_sensitive)` — прогон по книге → `{query, scopes, groups, clusters, labels, cluster_labels, files, total, scanned, skipped}`: `groups` — реестр `[(ключ, название, кластер)]`, `clusters` — `[(ключ, название)]`, в `files` каждый файл с `group`, `cluster`, `path`, `name`, `chapter`, `count`, `hits`. Лимитов на число совпадений нет: их рассекает на страницы только UI. И текст, и запрос проходят NFC (см. AGENTS §7).
