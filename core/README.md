# core/settings.py — реестр настроек (одно место истины)

Одна таблица, где живёт каждая настройка: ключ в `.env`, метка, тип, значение по умолчанию, подсказка и владелец-стадия. До реестра одно значение содержалось в четырёх местах — константы `core/stage.py`, константы и argparse `cli/*`, литеральные `default` в `web/stages.py`, и третий экземпляр комментариями в `templates/.env.example`; при этом глобальные ключи вида `CHUNK_SIZE`/`TIMEOUT` не читал никто (единственная форма записи была `<STAGE>_<FIELD>`). Теперь дефолт пишется один раз здесь.

Структура: субвкладка (`Group`, их пять: llm — Модель и сервер, transfer — Перевод, glossary — Глоссарий, checks — Проверки, book — Книга и файлы) → блок (`Block`, карточка) → настройка (`Setting`). Субвкладок пять; блоки веб-сервера (`server_net`, `server_run`) в реестре есть — их читает `web_values()`, но на экран они не попадают: `groups_payload()` их отфильтровывает. У блоков реестра есть флаг `llm`, по нему SPA подставляет значения профиля (настройки сервера профиль не перекрывает). Внешний вид (темы и кегли) в реестр не попадает как конфиг: предпочтения живут в localStorage, а их карточки SPA рисует своей локальной субвкладкой «Внешний вид». Ключ = имя в `.env`: у стадийных настроек `<STAGE>_<FIELD>`, у общих (LLM, рассуждения, `WEB_*`) — без префикса. Чипсы выбора (типы/поля) — `noenv`: тип `hidden`, в `.env` не пишутся, их состояние живёт в localStorage. У файловых полей есть `autofile` — автоподхват файла из пула проекта: конкретное имя (`source/donate.txt`) или маска с `*` (`source/*.epub` — первый файл пула с этим расширением); поле остаётся выбором человека, подхват срабатывает только на пустом и нет занятом вручную выборе. Служебные таблицы: `LLM_BLOCKS` (какие блоки относятся к профилю LLM — по ним SPA подставляет значения профиля), `SERVER_BLOCKS` (блоки веб-сервера), `LLM_STAGE_FIELDS` (общие LLM-поля — ОДНИ на все LLM-стадии, канонические имена флагов: шесть разных списков расходились), `STAGE_LLM_FIELDS` (он же по стадиям; пустой список и есть признак «без модели»), `LLM_ALIAS` (исторические имена флагов CLI: `jobs`→`threads`, `retries`→`max_retries`), `BLOCK_TITLES`, `NL`/`NL_LIT`.

`GROUPS` / `SETTINGS` / `BY_KEY` / `BY_BLOCK` / `STAGES` — сам реестр; `STAGE_TITLES` — название стадии ОДНО отсюда: его читают и карточки «Настроек», и спеки запусков (web/stages.py), иначе одна стадия звалась бы в двух местах по-разному; `groups()` — как рисовать; `settings_of(stage)` / `stage_fields(stage)` (поля формы стадии: настройки реестра в его порядке, затем общий диапазон глав) / `form_fields(stage)` (hidden-настройки в форму стадии не идут) / `defaults(stage)` — metadata и дефолты для спеки стадии (в `web/stages.py` их копировать нельзя); диапазон глав — параметр запуска книги, а не настройка: стадийных ключей `<STAGE>_START`/`<STAGE>_END` в реестре нет (у книги своего `.env` больше нет, а один общий диапазон на все книги не бывал верным); поля описаны один раз в `RANGE_FIELDS`, `RANGE_STAGES` — какие стадии их принимают и при каком режиме (та же форма условия, что у `when`), читаются `range_settings(stage)` / `range_fields(stage)` / `range_applies(stage,form)`; `chapter_range_error(start,end,last,first)` — одно правило проверки диапазона (конец не меньше начала, оба в пределах книги; пустое поле значит «вся книга»); его зовёт сервер (`web/api_stage._check_chapter_range` → 400 до запуска) и SPA (`UICore.chapterRangeError`), поэтому форма и запуск не расходятся; значение поля — только браузер; `env_key(stage,name)` — ключ поля; `llm_settings()` — LLM-поля одним блоком; `llm_form(stage,profile)` и `with_llm(stage,form,profile)` — подставляют значения профиля в form под историческими именами полей, поэтому сборка argv стадии не изменилась; `display_value(setting)` (секрет — `mask_secret` = `MASK_CHAR` × длина значения), `block_payload(block_id)` и `groups_payload()` — отдача реестра SPA. Касается ли настройка текущего режима стадии, решает сама настройка: `when` (И по всем парам), `when_any` (достаточно одной), `when_set` (перечисленные поля режима непустые — у булева поля это само значение: снятый чекбокс — «поля не задано»); у булевых полей значение сравнивается как `"1"`/`"0"`, пустой или отсутствующий режим ничего не режет, пустые условия — касается всегда. `applies(setting,form)` — один вопрос, `applicable_form(stage,form)` — форма запусков без лишних полей (её зовёт `web/stages.build_command`), bool-поля она отдаёт настоящими `bool`; мета поля режима уезжают в SPA вместе с `form_field()`, так что форма и команда считаются из одних данных.

Чтение (слоёв четыре: реестр → общий `.env` → профиль LLM → `os.environ`): `env_file()` (путь общего `.env`) / `file_values(env_path="")` (что выставлено в файле; явный `--env_file` подменяет общий файл, а не добавляет второй слой — иначе флаг менял бы половину конфига) / `layered_values(profile="", env_path="")` (поверх файла — значения выбранного профиля, затем непустые переменные окружения: окружение остаётся рубежом деплоя) / `effective(key)` (bool парсится, у textarea литерал «\n» разворачивается) / `stage_values(stage)` — эффективные значения стадии / `llm_values(profile="", env_path="")` — LLM-конфиг конвейера одним словарём: стадийных `PIPELINE_HOST`/`NER_MODEL`/`<СТАДИЯ>_API_KEY` нет, потоки, таймауты, повторы и отношение длин — тоже одна величина на весь запуск; `web_settings()`/`web_values()` — конфиг запуска сервера; `apply_cli_defaults(parser, stage)` вызывается в каждой точке входа `cli/` (дефолт реестра становится дефолтом argparse, поэтому булево поле стадии обязано приходить в argv явным `--flag`/`--no-flag` — отсутствие флага означает «как в реестре»); `is_on(value)` — единственное место, где булево значение приводится к `True`/`False`: `bool` и число — как есть, строки `.env` и формы — `1`/`true`/`yes`/`on` → `True`, `0`/`false` и пустое → `False`.

Запись: `sanitize(setting,value)` (значения — одной строкой: у textarea переносы сворачиваются в литерал «\n», у прочих — в пробел; `#` вне кавычек прячется в кавычки) / `write_values(ключ→значение)` перезаписывает общий `.env` по порядку реестра (пустое снимает ключ, без ключей файл удаляется) / `groups_payload()` — тот же реестр с текущими значениями для SPA; секретные поля отдаются маской (точка на символ значения); блоки веб-сервера (`SERVER_BLOCKS`) из выдачи фильтруются — в реестре они остаются, на экране сервера нет.

## Профили LLM (несколько наборов настроек модели)

Профиль — полный набор LLM-настроек (сервер, ключ, модель, таймауты, повторы, предел ответа, потоки, температура, отношение длин и весь блок рассуждений): 16 настроек блоков `llm_conn`/`llm_net`/`llm_run`/`llm_reasoning`. Нужен, когда серверов несколько: «домашний» и «облачной» раньше означали переписывание общего `.env` руками.

**General** — встроенный профиль по умолчанию: его значения и есть общий `.env`, поэтому данных в двух местах нет и без выбранного профиля система ведёт себя ровно как до профилей; он не переименовывается и не удаляется. Остальные профили — **один `llm_profiles.json` рядом с общим `.env`** (в Docker — в том же постоянном томе): `{"profiles":[{"id","name","values","created","updated"}]}`, в `values` — только переопределения (ключи `.env` верхним регистром), пустое поле профиля наследует General; последний удалённый профиль убирает файл совсем. Порядок в файле — порядок создания, а список в интерфейсе — General первым и дальше по алфавиту имени (NFC, без учёта регистра).

API: константы `PROFILE_DEFAULT` (`general`) / `PROFILE_DEFAULT_TITLE` / `PROFILE_ENV` (`NM_LLM_PROFILE` — переменная подпроцесса) / `PROFILES_NAME`; файлы — `profiles_file()` (сосед общего `.env`; файла конфига нет — корень репо) / `profiles_read()` / `profiles_write(list)` / `profiles()` (General первым, остальные — по алфавиту имени); чтение — `profile_get(id)` (пустой id и `general` — встроенный), `profile_values(id)`, `profile_display(id)` (General — эффективные значения конфига, остальные — свои переопределения; секрет под маской), `profile_slug(name,taken)` (латиница имени — slug, иначе `p1`, `p2`, …; id пишется один раз); CRUD — `profile_create(name,values,base_id="")` (без значений — копия выбранного `base_id`, по умолчанию General; `profile_defaults(base_id="")` — эффективные LLM-значения образца: общий `.env` → окружение → дефолт реестра, поэтому новый профиль выглядит копией, а не пустой формой; пустые ключи в профиль не пишутся), `profile_rename(id,name)` (id остаётся: на него ссылается выбор проекта), `profile_delete(id)`, `profile_save_values(id,values)` (значения сливаются с сохранёнными: страница сохраняет поля по одному, и ключа в запросе нет не тогда, когда его надо снять, а когда его не меняли; пустое значение переопределение снимает), `profiles_payload()`.

Куда выбор девается в web: поле **«Профиль LLM»** — ПЕРВОЕ поле формы каждой LLM-стадии (у стадии без модели поля нет), значение — состояние браузера по проекту+стадии (`localStorage nmProfile:<раздел>/<книга>:<стадия>`). У стадий одного проекта выбор свой: перевод на облачной модели, глоссарий — на домашней. `form_fields(stage)` ставит поле первым, `with_llm(stage,form)` читает его из формы и разбирает по историческим именам полей стадии, а подпроцесс получает `NM_LLM_PROFILE=<id>` — скрипты стадий читают реестр как читали, своего чтения `llm_profiles.json` у них нет. В CLI профиль — та же переменная окружения (или флаги `--host/--model` напрямую).

Дефолты подключения в реестре: `HOST=https://routerai.ru/api/v1`, `MODEL=google/gemma-4-31b-it`, `API_KEY` пусто.

# core/stage.py — общий слой стадий (флаги LLM, профиль сервера, прогресс)

Всё, что раньше кочевало между скриптами копией: блок LLM-флагов, разрешение сервера, сборка запроса, счётчик прогресса. Имена флагов — контракт форм web и SPA: их не переименовывать. До общего слоя каждая стадия жила своим набором чисел: у проверки перевода стрим-таймаут молча приравнивался к таймауту соединения, потоки отличались от скрипта к скрипту, а `reasoning=off` в логе означал «у скрипта пустой флаг», а не «рассуждений нет».

`add_llm_args` — общий блок флагов У ВСЕХ LLM-стадий один и тот же (`host`/`model`/`api_key`/`env_file`/`temperature`/`reasoning_*`/`timeout`/`stream_timeout`/`max_retries`/`max_tokens`/`threads`); у всех `default=None` — «значения нет, бери из общего конфига»; `aliases=True` — старые написания (`--retries`, `--jobs`, `--api-key`, `--env-file`, `--reasoning-effort`) тоже принимаются. `apply_cli_defaults` вызывается в каждой точке входа `cli/` — дефолты argparse стадии тоже из реестра. `add_check_prompt_arg`/`check_prompt` — режим `--check-prompt`: `check_prompt(args, name, contract, json_tags)` пишет вердикт о промпт-файле и возвращает True (main() сразу выходит 0); ставится ПЕРВЫМ делом main(), до `setup_stage` и чтения глав — логов запусков и артефактов стадии не появляется, профиль LLM не разрешается (сети нет вовсе), а сообщения проверки приходят в stderr предпросмотра.

`LlmProfile` + `resolve_profile(args, stage=, require_model=, require_server=, logger=)` — CLI > `os.environ` > общий `.env` (или явный `--env_file`) > дефолт реестра; `<СТАДИЯ>_HOST/MODEL` больше не слой, `/v1` дописывается, модель обязательна (`require_model=False` — режим предпросмотра), пустой сервер терпит только `require_server=False` (предпросмотр запроса в сеть не идёт). В профиль, кроме подключения, попадают `threads`: это общая настройка конвейера, а не собственное число стадии; `env_data` — уже разрешённый послойный конфиг (из него же `LLM_EXTRA_BODY_JSON`). Повторы при отсутствии правок в профиль НЕ входят: их цена у проверки глоссария и у проверки перевода разная, поэтому число стадийное (`NER_CHECK_RETRY_EMPTY`, `TRANSLATE_CHECK_LLM_RETRY_EMPTY`).

`describe_profile(profile)` — строки лога о разрешённом конфиге: пишет их `resolve_profile`, а не тело стадии (иначе стадия отчитывается своим пустым флагом). Рассуждения и провайдер печатаются как реальные ключи payload, а не пересказом режима. `complete_until(stage, prompt, data, accept=, attempts=, note=)` — одна политика повторов на конвейер: `1 + attempts` запросов, где `attempts` — число дополнительных повторов стадии (0 — по умолчанию, запрос один); ответ, который не устроил `accept` (пустой, пустой список `[]`, нераспарсенный) — не ошибка, а повод спросить ещё раз, последний ответ берётся как есть, ошибка LLM возвращается сразу (её считает `MAX_RETRIES`).

`LoggedStage` + `new_stage` (лог стадии и `log_argv`) / `Stage` + `bind_profile` + `setup_stage` (LLM-режим отдельно от лога: `--apply` и `--compile-chapters` не требуют настроенного сервера; `stage.complete(prompt, данные)` — один вызов стрима, `stage.preview()` — режим предпросмотра) / `Progress` (в CLI — бар tqdm с обязательным `unit=`, в web — только `@@PROGRESS@@`; строка счётчика в лог стадии — редкой строкой: каждые `LOG_EVERY` шагов или не чаще раза в `LOG_EVERY_SECONDS` секунд, финальную строку пишет `close()` — прежний счётчик на каждый шаг заливал кольцевой буфер запусков тысячами одинаковых строк) / `REASONING_EFFORTS`.

# core/transport.py — единственная точка выхода в сеть (единственный HTTP-клиент)

HTTP-клиент в проекте один — `httpx`, и живёт он **только** здесь: `cli/`, `web/` и `run.py` не импортируют HTTP-библиотеки вовсе (страж `tests/test_architecture.py`; он же не даёт вернуть «запасной» клиент). Запасной не нужен: второй клиент — это второй адаптер, второй путь ошибок и второй набор тестов ради поведения, которое вызывающий не видит. Что даёт общий клиент: переиспользование соединений (конвейер бьёт в один сервер сотнями запросов) и раздельные connect/write/read таймауты.

`open_stream(url, *, headers, payload, connect_timeout, read_timeout)` — единственный способ POST-а в LLM; возвращает контекстный менеджер `ResponseStream`: `status_code`, `headers`, `iter_lines()` (байтовые строки тела по `\n`, `\r` отрезан, пустые строки отдаются как есть — пустая строка SSE = конец события; из строк события собирает `core.common.iter_sse_events`, он же видит `[DONE]` и finish_reason). Выход из контекста закрывает соединение, в том числе при `break` в середине стрима; запрос уходит на входе в `with`, поэтому «сервер лежит» прилетает именно там и тоже нормализуется.

Ошибки: `TransportError` (базовый) / `ConnectTimeout` (таймаут connect, отказ соединения, недоступен хост) / `ReadTimeout` (сервер молчит в теле; сюда же — нет соединения в пуле) / `BrokenStream` (обрыв тела, битый gzip/декодер). Гигиена стрима и политика ретраев живут в `core/common.py`. `open_get(url, *, headers, timeout=15, follow_redirects=False)` — GET тем же `ResponseStream`ом: нужен проверке сервера (`core.common.probe_server`) и скачиванию файлов (GitHub отдаёт ассеты редиректом); рабочий запрос к LLM остаётся POST-ом. `open_json_get(url, *, timeout=15)` — короткий GET с ожиданием JSON-словаря в ответе (GitHub Releases); не-2xx и не-JSON — `TransportError`. `ResponseStream.iter_bytes()` — сырое тело кусками (бинарные скачивания: `iter_lines` портит zip переносами). Прочее API: `client()` (общий `httpx.Client`), `reset_client()` (сброс — тестам), `BACKEND` (`"httpx"`), `python3 -m core.transport` — сводка.

# core/deps.py — реестр внешних зависимостей (активный стек в лог)

Роль — не имя пакета: роль закрыта, если работает хотя бы один её кандидат; кандидат без модуля — встроенный stdlib-фолбэк, он «установлен» всегда. Роли: HTTP-транспорт LLM (один кандидат `httpx`, обязателен — фолбэка сознательно нет), разбор `.env` (один кандидат `python-dotenv`, обязателен), поиск терминов по главам (pyahocorasick, иначе regex-фолбэк), прогресс-бары CLI (tqdm, иначе счётчик только строками лога), тесты (pytest + pytest-xdist). Только чтение: модуль ничего не устанавливает и поведение не меняет — его выбирают люди и лог.

`ROLES` (роли и кандидаты в порядке предпочтения) / `status()` → строки отчёта `{role, where, required, active, installed, degraded, pip_missing}` (`degraded` — роль на фолбэке: не ошибка, просто медленнее) / `format_status()` — одна строка для баннера/лога (web-сервер пишет её при старте) / `missing_hint()` — что доустановить одним pip-ом / `main()` — таблица для `python3 -m core.deps`.

# core/search.py — поиск по текстам книги (обычный проход, без индексов)

Книга — сотни файлов по несколько килобайт: обычный проход читает их за доли секунды, а FTS5-индекс означал бы второй слой (построение, инвалидация, разъезд с правками) при нулевом выигрыше. Индексов и кешей нет намеренно — результат всегда равен содержимому файлов.

Реестр групп (`SearchGroup`-кортежи `SEARCH_GROUPS`) решает, *что* именно читает поиск: `chapter`/`translated`/`redacted`/`polished` — артефакты стадий во всех папках глав, `ner` — `ner.json`, `notes` — `notes.md` и `source/info.md`, `prompts`/`reports`/`logs` — обход каталогов `prompts/`, `tmp/`, `logs/` (только текстовые расширения `TEXT_EXT`). `GROUP_IDS` — ключи, `GROUP_LABELS` — подписи для интерфейса, `DEFAULT_SCOPES` — что ищется по умолчанию (`chapter,polished,ner,notes`: тексты книги и глоссарий, без служебных каталогов).

API: `iter_project_files(project_dir, scopes=None, *, max_file_bytes)` — обход (главы — по номеру, каталоги — вниз по именам; пустые и oversized файлы пропускаются); `find_in_text(text, query, *, context, case_sensitive)` — все совпадения `[{line, start, end, text}]`, где `line` — номер строки с 1, `text` — строка, обрезанная до ±`context` **СИМВОЛОВ** (обрезок помечен «…»), `start`/`end` — границы совпадения внутри этого фрагмента (`text[start:end]` — само совпадение); `search_project(project_dir, query, scopes=None, *, context, case_sensitive)` — прогон по книге → `{query, scopes, groups, clusters, labels, cluster_labels, files, total, scanned, skipped}`: `groups` — реестр `[(ключ, название, кластер)]`, `clusters` — `[(ключ, название)]`, в `files` каждый файл с `group`, `cluster`, `path`, `name`, `chapter`, `count`, `hits`. Лимитов на число совпадений нет: их рассекает на страницы только UI. И текст, и запрос проходят NFC (см. AGENTS §7).

# core/uistate.py — состояние книги на диске (tmp/ui_state/)

Состояние интерфейса делится по природе данных: что описывает книгу (значения форм стадий, профиль LLM по стадиям, чипсы, место работы во вкладках, столбцы и фильтры глоссария, запрос «Поиска») лежит в книге; что описывает устройство (тема, кегль редакторов и предпросмотра, субвкладка «Настроек», сортировка «Файлов») остаётся в `localStorage`. Переезд книжной половины означает, что смена браузера, домена или устройства её не теряет, а копия книги наследует состояние вместе с `tmp/`.

Файл ОДИН на книгу — `state.json`. Состояние книги — её свойство, а не свойство устройства: файл на устройство (`<id>.json` по cookie) делил одну книгу на несколько правд (два компьютера и два домена видели разные диапазоны глав), а каталог рос новым json на каждый браузер, домен и чистку cookie. Несколько писателей не теряют правки друг друга: запись читает файл и накладывает только присланные ключи, а у присланных объектов сливаются поля — правка одного поля формы не стирает соседние. Значение `None` снимает ключ, `None` внутри объекта — поле (снятая галочка не воскресает). Запись возвращает слитое состояние: клиент держит его снимок для показа, иначе его поля расходились бы с книгой до перезагрузки. Файлы прежней версии (`<id>.json`, `pending.json`) сливаются в общий при первом чтении или записи и затем удаляются — состояние, оставленное до обновления, не теряется.

Ничего своего у состояния нет: это словарь ключей интерфейса (`nmTab:раздел/книга`, `runVals:раздел/книга:стадия`, `nmProfile:…`), поэтому слой не знает ни одного имени поля, а новый ключ SPA не требует правок здесь. `tmp/` исключён из истории контрольных точек (`web/history.py`): состояние — не содержимое книги, и возврат к точке не должен откатывать вкладки.

API: `UI_STATE_DIR` (`tmp/ui_state`) / `UI_STATE_FILE` (`state.json`) / `UI_STATE_VERSION` / `ui_state_dir(project_dir)` — каталог состояния / `ui_state_read(ddir)` → `{ключ: значение}` — состояние книги (файла нет — слияние файлов прежней версии в порядке записи: `updated`, без отметки — `mtime`) / `ui_state_write(ddir, payload)` → состояние целиком — только изменённые ключи (`None` снимает ключ или поле, `atomic_write` под локом, `UI_STATE_VERSION` и `_deleted` в файле, влитые файлы прежней версии удаляются).

# core/archive.py — упаковка проекта в один файл и обратная распаковка

Готовая книга — тысячи мелких файлов (боевая: 10 243 файла, 197 МБ на диске), хотя работа по ней не идёт. Упаковка в один файл даёт 197 → 54 МБ и один файл вместо десяти тысяч. Формат — обычный `tar` с потоком `zstd`: открывается без программы (7-Zip, `tar --zstd`, `zstd -d | tar -x`, Windows 11). Своего формата нет намеренно — «архив», который читается только NovelMaestro, перестаёт быть архивом.

Константы: ARCHIVE_EXT (".nmz") / ARCHIVE_MANIFEST (".nm_archive.json" — ПЕРВЫЙ член: имя, дата, версия, счётчики; читается из головы за миллисекунды, поэтому список архивов не распаковывает книги) / ARCHIVE_DIR (".archive" внутри раздела) / ARCHIVE_VERSION / COMPRESSION_LEVEL (9: 25,6 МБ / 0,4 с на боевой книге; 19 даёт 20,4 МБ, но 13,8 с — заметная пауза при нажатии кнопки) / ArchiveError.

Пути и сведения: archive_dir / archive_path (`<раздел>/.archive/<имя>.nmz`) / archive_size (0, если файла нет) / archive_free_space / archive_manifest (пустой словарь по битому файлу — карточка скажет «повреждён», страница не упадёт) / is_temp_name (имя служебное: `.nm_restore_*` или `*.nmz.tmp` — так выглядят недоделанная распаковка и упаковка, это не книга: `project_items` их не показывает).

Работа: pack_project(src, dst, skip=..., progress=..., manifest_extra=...) — атомарно (`<dst>.tmp` + `os.replace`; оборванная упаковка оставляет книгу целой), `skip` — папки ТОЛЬКО верхнего уровня, `progress(done, total)` зовётся раз в 64 файла (колбэк стадии пишет строку в лог, на каждый файл это сотни строк), симлинки не уходят (побег за пределы книги), пустые каталоги остаются (каркас `chapters/`+`prompts/`); unpack_project(archive, dst, progress=...) — через временный каталог, занятое место — ошибка (вызывающий решает, что делать с проектом на месте).

Сжатие: backend() → `{id, label, ext, open_write, open_read}`, порядок — `zstandard` (pip, `threads=-1`) → stdlib `compression.zstd` (Python ≥ 3.14) → `gzip`. Последний бэкенд есть всегда, поэтому кнопка «Архивировать» не падает ни в Docker, ни в портативной сборке без пакета — архив просто больше. archive_available() — можно ли упаковывать (сейчас всегда да).

# core/update.py — как эта копия установлена и как она обновляется

Релизы живут на GitHub Releases (тег `v*`, `VERSION` = тег без `v`), но путь обновления зависит от того, как программа установлена: у каждой установки свой способ, и общий для них только список данных, которые не меняются никогда. Способ определяется по маркерам в корне кода (`install_kind`), своих переключателей у обновления нет.

Способы установки (`KIND_*`, порядок проверки — docker первый): `docker` (маркер `.docker`, который кладёт Dockerfile) — контейнер не заменяет собственный образ, `update_mode` возвращает `command` и интерфейс показывает команду хоста `HOST_COMMAND`; `portable` (маркер `START.txt`, который кладёт упаковщик) и `tree` (копия исходников без `.git`) — режим `zip`: файлы архива релиза кладутся поверх текущих, ничего не удаляется; `git` — режим `git`: своя ветка перематывается на релиз (`ff-only`) через dulwich — тот же git-механизм, что у вкладки «История»; бинарника git в Docker и в портативной сборке нет, поэтому он не участвует.

Данные пользователя вне дерева кода: `PROTECTED_PATHS` (книги, логи, очередь запусков, профили LLM, `.env`, маркер образа) и `PROTECTED_DIRS` (`.git`, `.venv`, `.tmp`, кэши, `job_logs` и встроенный интерпретатор `python` — он занят процессом). Из `templates/` обновление проходит только по встроенным частям: набору `core/projects.py::TEMPLATE_PROTECTED` (`General/`) и шаблону `.env.example` — их поставляет релиз; наборы, созданные пользователем (`templates/Custom/…`), остаются как есть. Подозрительные пути архива (`..`, диск) считаются защищёнными: их не пишем ни в каком режиме.

Перезапуск — часть обновления, а не отдельный ритуал: на диске код новый, а процесс до перезапуска работает старым. В git и tree-установке сервер делает это сам: `schedule_restart` поднимает наблюдателя (свой сеанс, код `_WATCHER_CODE`), тот ждёт исчезновения `/proc/<pid>` сервера (порт освобождается не мгновенно, а второй сервер на другом порту — это два интерфейса об одних книгах) и запускает сервер той же точкой входа и теми же флагами (`RESTART_VALUE_FLAGS`, `RESTART_SWITCH_FLAGS`); после этого процесс сворачивается своим `SIGTERM`, чтобы `web/main.py` штатно остановил активные запуски. Портативная сборка (окно с занятым `python.exe`) и Docker (контейнер перезапускает хост) перезапускаются руками — об этом говорит `RESTART_NOTES`.

API: `install_kind(root=None)` / `update_mode(kind)` / `installed_version(root=None)` (содержимое `VERSION`) / `version_tuple(version)` — сравнимый кортеж чисел / `update_available(current, release)` / `release_notes(body)` → `(notes, changes)`: строку «Full Changelog: <ссылка>» автозаметки GitHub вырезает из заметок — это ссылка, а не описание / `latest_release()` → `{ok, tag, version, name, url, published, notes, changes}`; сетевые ошибки НЕ бросаются (отчёт `{ok: False, error}`) / `release_asset_url(tag)` — zip портативной сборки релиза (`ASSET_PREFIX`) / `download_asset(url)` — сырое тело ассета / `is_protected(rel)` / `host_command_hint()` — текст отказа для Docker / `apply_update(root, tag, kind=None, log=None)` → `{kind, mode, from, to, branch|files+skipped, note}`: `note` — смена `requirements.txt` (без установки пакетов новая версия может не подняться, это не ошибка). Перезапуск: `restart_supported(kind)` / `restart_command(argv)` / `restart_plan(argv, kind, root, allowed)` → `{kind, mode, auto, command, note}` / `schedule_restart(...)` — то же плюс наблюдатель и свой сигнал. Ошибки — `UpdateError` человеческим текстом. Сеть — только через `core.transport` (`open_json_get`, `open_get` с `follow_redirects`); `log` — необязательный колбэк строк хода.

Веб-слой держит одно состояние на все вкладки: кеш последнего релиза и состояние потока применения (`web/api_common.py`). Проверка проходит при запуске сервера в отдельном потоке (`WEB_UPDATE_CHECK`, по умолчанию включена) и по кнопке «Проверить», сессия отдаёт кеш без сети. Флаг `--no-restart` (`WEB_RESTART=0`) выключает автоперезапуск: его передаёт dev-серверу `dev.sh`, чтобы PID-файл не потерял процесс.
